## 1. 기록 유실 가능성이 있는 종료·복구 처리

위치: `app/api/lecture-sessions/route.ts:620`, `:631`, `app/classroom/use-lecture-recorder.ts:247`, `:1375`.

- 종료 API는 전달된 세그먼트를 검증하면서 **앞 5,000개만** 사용한다. 초과·제외 항목을 오류로 알리지 않는다.
- 클라이언트는 전체 기록을 종료 요청과 localStorage 복구 사본에 담지만, 응답이 2xx이면 복구 사본을 지운다.
- 이미 completed인 수업에 재전송한 요청은 누락 구간 저장 이전에 성공 응답을 반환한다.

예: 5,001번째 구간의 실시간 저장이 실패한 뒤 종료하면, 종료 요청에서도 그 구간을 잘라 버릴 수 있다. 성공 응답을 받은 클라이언트가 마지막 복구 사본까지 지운다. 다른 탭의 정리 동작이 먼저 completed로 바꾼 경우에는 5,000개 이하의 미저장 구간도 재전송 시 누락될 수 있다. 운영에서 실제 사용자 데이터가 유실됐다는 것을 입증한 것은 아니다.

**수정안:** 이미 확인된 구간은 재전송하지 않고 미확인 구간을 크기가 제한된 배치로 저장한다. 서버가 배치별 저장 결과를 명시하고 모든 구간이 확인된 뒤에만 완료 처리·복구 사본 삭제를 수행한다. completed 상태의 복구도 기존 소유권·과금 이력을 보존하는 별도 경로로 허용해야 한다. 단순히 completed 재생성을 무제한 허용하면 이전 비용 우회 문제가 재발한다.

연관 문제: `route.ts:350`, `:409`의 복구 색인은 5,000개만 읽는데 정상 완료는 `:722`에서 50,000개를 읽는다. 청크가 일부 있으면 복구 색인을 건너뛰는 조건과 함께 후반부 검색 누락을 만들 수 있다. 색인 완결 상태를 청크 존재 여부와 분리해야 한다.

**완료 기준:** 5,001번째 미저장 구간, completed 수업의 복구 재전송, DB 일시 오류, 중복 종료에서 구간 보존·중복 과금/색인 방지가 모두 통과해야 한다.

## 2. 수업을 여는 동작이 다른 기기의 녹음을 멈출 수 있음

위치: `app/classroom/workspace-client.tsx:1218`, `app/api/lecture-sessions/route.ts:469`, `supabase/migrations/20260901010000_pause_lecture_sessions.sql:22`.

수업을 열 때 DB 상태가 recording이면 클라이언트가 자동 pause를 보낸다. 현재 탭이 이전 녹음을 소유했다고 가정하지만, 동일 계정의 다른 탭·기기는 여전히 녹음 중일 수 있다. 운영 pause 함수는 계정 소유권을 확인하지만 활성 relay를 확인하지 않는다.

pause 뒤 relay의 다음 상태 확인에서 수업 종료 상태를 감지해 연결이 닫힐 수 있다. 따라서 이 문제는 Wi-Fi 장애와 별개로 발생할 수 있다. 사용자가 과거 겪은 모든 연결 오류의 원인이라고 단정하지 않는다.

**수정안:** 수업 열기는 조회만 한다. 복구가 필요하면 별도 서버 동작에서 활성 녹음 lease가 없는지 원자적으로 확인하고 stale 상태만 복구한다. 활성 상태에는 “다른 탭 또는 기기에서 녹음 중”을 표시한다. 정상 녹음 소유자의 수동 pause와 복구 pause를 구분한다.

**완료 기준:** 두 번째 탭에서 같은 수업을 열어도 첫 탭의 capture·heartbeat·과금 lease가 유지되고, 실제 끊어진 세션은 정상 복구돼야 한다.

## 3. 생성이 느린 가장 유력한 인프라 원인: 앱과 DB의 거리

확인된 사실:

- 운영의 `/api/classrooms`, `/api/lecture-sessions`, `/api/ask`, `/api/materials`, `/classroom` 함수는 **iad1(미국 동부)**에 배치돼 있다.
- Supabase 연결 지역은 **ap-northeast-2(서울)**이다.
- 한국에서 읽은 운영 응답의 `x-vercel-id`도 `icn1::iad1`을 표시한다.
- DB 전체 크기는 약 **21.6MB**, 통계상 lecture_sessions 약 42행·transcript_segments 약 2,564행이다. 추정 행 수이며 정확한 이용자 규모로 해석하지 않는다.

운영 `pg_stat_statements`에서 관련 PostgREST 호출을 분류한 누적 통계:

| 범주 | 호출 수 | DB 실행 평균 |
|---|---:|---:|
| 강의실 관련 | 565 | 0.429ms |
| 수업 관련 | 6,198 | 0.249ms |
| 스크립트 관련 | 4,117 | 1.451ms |
| 공유 요청 제한 RPC | 8,448 | 1.149ms |
| 크레딧 조회 RPC | 992 | 5.483ms |

호출 수 10회 이상인 SQL을 대상으로 한 가중 평균이며 과거 배포·작업도 포함한다. 각 API 전체 응답 시간이나 현재 p95가 아니다. 일부 쿼리 최대값은 더 높다. 그래도 현재의 초 단위 체감을 DB의 큰 데이터량만으로 설명할 근거는 약하다.

강의실 생성은 서버에서 `getUser → 공유 요청 제한 RPC → INSERT returning`을 순서대로 기다린다. 특정 강의실에서 녹음을 시작하면 소유권 조회·중복 생성 확인·생성/전환·자료 연결 등의 왕복이 더 붙는다. 위치: `app/api/classrooms/route.ts:14`, `:19`, `:59`; `app/api/lecture-sessions/route.ts:230`, `:250`, `:266`, `:280`.

**수정안:** 먼저 DB를 자주 호출하는 앱 함수를 서울 근처에 배치한 후보와 비교한다. 해외 이용자가 있어도 API 내부에서 DB를 여러 번 왕복한다면 DB와의 거리를 먼저 줄이는 것이 합리적이다. 관련 DB 검증·쓰기는 소유권을 보존하는 트랜잭션/RPC로 합칠 수 있다. 인증·동의·크레딧·동시 녹음 제한을 제거하는 방식으로 최적화하면 안 된다. [Vercel의 함수 지역 안내](https://vercel.com/docs/functions/configuring-functions/region)도 데이터 소스와 가까운 배치를 권장한다.

**측정 한계:** 실제 로그인 사용자의 생성·저장 작업을 새로 실행하지 않았으므로 “몇 초 빨라진다”는 수치는 아직 없다. 새 수업 생성 p50/p95와 auth/rate-limit/DB 단계 시간을 먼저 계측하고 같은 입력으로 후보 배포와 비교해야 한다. 무인증 401 응답에서 관측한 0.35~1.30초는 해당 로그인 경로의 측정값을 대신하지 않는다.

## 4. 저장 완료를 기다리는 동안 AI 색인까지 동기 실행

위치: `app/api/lecture-sessions/route.ts:706`, `:722`, `:94`; `app/classroom/use-lecture-recorder.ts:1333`.

서버는 완료 상태를 저장한 뒤 전체 스크립트를 다시 조회하고, OpenAI 임베딩 생성·기존 청크 교체·색인 작업 완료까지 기다린 다음 응답한다. 임베딩 호출 설정의 timeout은 60초다. 이것이 정상 저장에 항상 60초가 걸린다는 뜻은 아니다. 클라이언트에서는 응답 후 강의실 목록과 크레딧 갱신도 직렬로 기다린다.

**수정안:** 기록 저장과 영속적인 색인 작업 등록까지만 기다려 “저장됨”을 표시한다. 검색 준비는 별도 작업이 처리하고 실패 시 재시도한다. 단순 `void promise`만 붙여 응답하면 서버리스 실행 종료 시 작업이 사라질 수 있으므로, 기존 index-job/예산 예약을 이용한 영속 작업 상태가 필요하다. UI는 목록을 반환된 수업으로 먼저 갱신하고 크레딧은 별도로 갱신한다.

## 5. 수정 후 전체 이력을 다시 읽는 중복 작업

위치: `app/classroom/workspace-client.tsx:1169`, `:936`, `:957`, `:776`; `app/lib/classroom-data.ts:10`.

강의실 PATCH는 수정한 행을 반환하지만 화면은 이를 사용하지 않고 전체 `/api/classrooms`를 다시 기다린다. 제목 변경·수업 이동·자료 업로드용 draft 생성 뒤에도 전체 목록 갱신이 붙는다. 목록 조회는 모든 수업을 500행 단위로 끝까지 읽는다.

강의실 **신규 생성**은 이미 POST 응답으로 목록을 갱신한다. 이 경로까지 중복 재조회가 있다고 판단하지 않았다. 또한 proxy는 `/api`의 인증 중복을 이미 생략한다.

**수정안:** 변경 응답으로 해당 항목만 즉시 교체하고 필요한 경우 뒤에서 재검증한다. 오래된 수업은 화면에서 더 보기/페이지 방식으로 읽는다. 운영에는 `(user_id, started_at DESC, id)` 형태의 이력 정렬용 인덱스가 없지만 현재 DB가 작고 쿼리도 빠르므로 인덱스 추가는 실측 실행 계획과 데이터 증가를 보고 결정한다. [Supabase 인덱스 안내](https://supabase.com/docs/guides/database/query-optimization).

## 6. 요약 삭제 후 같은 구간을 다시 유료 생성 가능

위치: `app/api/lecture-summaries/route.ts:88`, `:97`, `:118`, `:137`; `supabase/migrations/20260902030000_low_audit_fixes.sql:27`.

운영에서 authenticated 사용자는 자기 `lecture_summaries` 행을 INSERT/UPDATE/DELETE할 수 있다. 생성 API는 기존 요약 행의 존재로 중복을 판단한다. 사용자가 요약을 직접 삭제하고 다시 호출하면 이미 요약한 충분히 긴 구간을 플랫폼 키로 재생성할 수 있다. 분당 20회 제한과 동시 생성 lease는 있지만 삭제·순차 재생성에 대한 일일 비용 예산은 없다. 운영에서도 기존의 완성된 요약 구간에 이 경로가 존재한다.

**영향:** 본인 수업을 전제로 한 API 비용 악용 가능성이다. 다른 사용자의 정보가 읽힌다는 뜻은 아니며 실제 유료 재생성 공격을 수행하지 않았다.

**수정안:** AI 생성 결과의 브라우저 직접 쓰기를 철회하고, 서버에서 수업 소유권을 확인한 뒤 저장한다. 결과 행 삭제와 독립된 구간별 작업 완료·재생성 예산을 유지한다. 요청 빈도뿐 아니라 유료 작업량을 제한하는 방향이다. [OWASP API 리소스 통제](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/).

## 7. PDF 압축 해제 후 처리량에 상한이 없음

위치: `app/api/materials/route.ts:59`, `:281`, `:290`.

20MB 파일·500페이지 제한은 있지만 추출된 전체 글자 수·청크 수·토큰 수를 제한하지 않는다. PDF 결과를 모두 모아 임베딩 요청 하나로 보낸다. 일반 텍스트 파일의 50만 자 제한도 PDF에는 적용하지 않는다.

격리된 작은 재현에서 실제 PDF.js가 **1,109바이트·1페이지 PDF를 500,001자·278청크로 추출**했다. 합성 자료를 메모리에서만 처리했으며 운영 업로드·네트워크·유료 API는 사용하지 않았다. 대형 메모리 소진이나 운영 장애가 발생했다고 주장하지 않는다.

**수정안:** 누적 추출 글자·청크·토큰 예산을 초기에 검사하고, PDF 파서에 처리 시간·메모리 한도를 둔다. 정상적인 큰 강의자료는 분할 처리 상태와 재시도를 제공해야 한다. 원본 파일 크기만 제한하는 것으로 압축 해제 후 비용을 통제할 수 없다.

## 8. DB에서 수업과 강의실 소유자의 일치를 강제하지 않음

위치: `supabase/migrations/20260902000000_lock_billing_columns.sql:18`, `supabase/migrations/20260822010000_classrooms.sql:86`.

운영의 lecture_sessions는 본인 user_id에 대한 RLS와 classroom_id의 단일 FK를 가지고 있고, authenticated INSERT에 classroom_id가 허용돼 있다. 앱 API는 강의실 소유권을 검사하지만, 직접 Data API 요청은 다른 계정의 알려진 classroom UUID와 본인 수업을 연결할 수 있는 권한 구조다.

**영향:** 잘못된 관계 연결·존재 여부 추측·앱 생성 제한 우회다. 현재 조회/검색 경로의 소유권 방어를 고려하면 다른 사용자의 강의 본문 유출은 확인되지 않았다. 운영에 해당 행을 삽입하는 시험도 하지 않았다.

**수정안:** `(classroom_id,user_id)` 복합 소유권 FK 또는 같은 수준의 DB 검사로 관계를 보장한다. 직접 생성이 불필요하면 서버 소유권 검사 후 생성으로 통일하고 브라우저 쓰기 권한을 축소한다. 기존 불일치 데이터 집계를 먼저 확인한 뒤 마이그레이션해야 한다.

## 추가 점검 후보와 확인 한계

- 휴대폰 중계는 방마다 제한하지만 계정별 활성 방 총량 제한이 없다. API 10회/분과 Worker 3시간 TTL을 조합하면 많은 방을 유지할 수 있다. STT 크레딧·동시 녹음 방어와 별개의 중계 비용 문제다. 현재 Worker 소스와 실제 운영 배포의 일치까지 이번에 검증하지 않았으므로 후보로 분류한다. 계정별 활성 방 상한과 미연결 초대의 조기 만료를 권한다.
- 자료 20개 상한은 조회와 저장 사이가 원자적이지 않아 동시 업로드에서 초과할 수 있다. 100회/일 제한은 존재한다. 예약/잠금 기반으로 처리할 수 있다.
- 공유 rate limiter는 일부 DB 오류에서 프로세스별 제한으로 돌아간다. 장애 시 인스턴스 수만큼 총량이 늘 수 있다. 유료 처리 경로는 별도 예산 확인이 성공한 경우에만 진행하는 방식이 낫다. 당장 모든 녹음 연결을 fail-closed로 바꾸면 안정성을 해칠 수 있으므로 경로별 정책을 구분해야 한다.
- 이전 문서에는 정기 파일 삭제·자동 백업 실행 확인이 남아 있다. 이번 운영 삭제 큐는 0건이었지만 자동 예약·복원 성공을 다시 검증한 것은 아니다. “백업이 완성됐다”는 판단은 보류한다.
- 수업 생성/저장에 auth·DB·index 구간별 타이밍을 남기는 관측성이 필요하다. 현재 확인한 최근 요청 로그 100개에는 분석에 필요한 단계별 시간이 없다. 이번 무인증 검사 응답을 포함한 표본이므로 이를 사용자 성공률이나 서비스 전체 장애율로 계산하지 않았다.

## 유지해야 하는 정상 방어

- 이전에 적용한 생성 청크/노트/자료 소유권 FK와 Storage 직접 쓰기 제한을 확인했다. 위의 누락된 관계를 추가 보완해야 한다.
- 관리자 기능은 검증된 이메일 allowlist를 사용한다. Paddle은 원문 서명·시간 범위·가격/주문/고객 연결·원자적 결제 처리를 확인한다.
- 운영 무인증 classrooms·lecture-sessions·materials는 401, admin은 403, live-assist POST와 lecture-summaries POST는 401이었다. phone-mic의 Origin 없는 POST는 403으로 차단됐다. 이는 권한 있는 다른 계정 간 침투 시험을 대신하지 않는다.
- 운영 recording preflight에서 CSP, relay WSS, AudioWorklet, Worker, microphone/display-capture 권한과 relay health가 통과했다. 실제 마이크·전사·재연결 시험은 아니므로 녹음 안정성 결함을 상쇄하지 않는다.
- `npm audit --omit=dev`는 현재 0건. 자체 권한/비용/복구 결함은 패키지 감사에 나타나지 않는다.
- 관련 기존 75개 테스트가 통과했다. DB·공급자 모의 테스트이며 이번에 발견한 모든 실패 조건을 다루는 테스트라는 뜻은 아니다.

테스트 명령: `node --experimental-strip-types --experimental-test-module-mocks --test app/api/billing/webhook/route.test.ts app/api/materials/route.test.ts app/api/phone-mic/route.test.ts app/lib/billing.test.ts workers/phone-mic/index.test.mjs`.

토큰·쿠키·사용자 본문을 제외한 운영 측정 결과는 [검토 근거 JSON](performance-security-review-2026-09-11-evidence.json)에 기록했다.

## 권장 구현 순서와 승인 가능한 변경 범위

1. **기록 보존·녹음 안정성:** 자동 pause 제거와 안전한 stale 복구, 미저장 구간 배치 확인, 완료 후 복구, 색인 완결 상태 수정. 두 탭·긴 수업·중복 완료 회귀를 우선 추가한다.
2. **새 보안 결함:** 요약 결과 쓰기 권한/재생성 예산, PDF 추출 예산, 누락된 부모 소유권 검사를 함께 수정한다.
3. **즉각적인 속도:** 저장 후 목록 재조회 제거, 앱/DB 지역을 맞춘 후보 배포 비교. auth·rate-limit·DB 타이밍을 개인정보 없이 계측한다.
4. **저장 후속 처리:** 영속 색인 작업 등록 후 즉시 응답하고 비동기 작업·재시도 상태를 제공한다. 인증·크레딧·동시 녹음·색인 예산은 그대로 유지한다.
5. **증가 대비:** 목록 페이지화, 실행 계획에 근거한 인덱스, 휴대폰 방·자료 업로드 동시 사용 예약을 보완한다.

각 변경은 저장소의 `docs/recording-change-checklist.md`에 따라 로컬·후보·운영 preflight와 해당 회귀를 통과해야 한다. 녹음 경로·지역·배포가 바뀌면 실제 microphone/tab-audio 시작·pause/resume·종료도 별도로 확인한다. 녹음 중인 탭을 새로고침하거나 다른 기기의 연결을 종료해 검증하지 않는다.

현재 단계에서는 값비싼 모델 변경·새 서버 도입·DB 증설을 먼저 권하지 않는다. 확인된 대기 구조와 비용/저장 통제부터 고친 뒤 측정값으로 다음 투자를 결정한다.
