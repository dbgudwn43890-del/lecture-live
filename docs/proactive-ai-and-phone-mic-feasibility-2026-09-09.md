# 관리자 자동 답변 · 휴대폰 마이크 가능성 검토

2026-09-09. 검토만 수행. 기능 구현, 운영 설정 변경, 실제 음성·AI API 호출은 하지 않았다.

후속 작업: 관리자 자동 답변은 [구현 기록](live-assist-implementation-2026-09-09.md)을 기준으로 확인한다. 아래는 최초 검토이며, 핵심 2~3개·펼치기 방식은 후속 요청에 따라 사용하지 않는다. 휴대폰 마이크는 아직 검토 단계다.

## 결론

두 기능 모두 현재 Lecue에 추가할 수 있다. 자동 답변은 관리자 실험으로 먼저 도입하기 적합하다. 휴대폰 마이크는 공급자를 바꾸지 않고 구현할 수 있으나 녹음 기기와 열람 기기의 상태 분리가 필요하다. 두 기능은 별도로 켤 수 있게 만들고 이후 함께 사용할 수 있다.

## 관리자 전용 자동 답변

대상은 사용자가 지정한 `dbgudwn43890@gmail.com` 계정이다. 기존 `/api/admin`의 서버 인증 패턴은 참고하되 이 실험의 권한은 해당 계정에만 별도로 부여한다. 구현 시 검증된 Auth 계정을 서버에서 확인하고 사용자 UUID에 권한을 연결한다. 현재 해당 실험 권한이 설정되어 있다는 뜻은 아니다. 클라이언트 이메일, URL 파라미터, localStorage는 권한 근거로 사용하지 않는다. UI뿐 아니라 판단·생성·조회 API 모두 권한과 세션 소유권을 검사한다.

권장 흐름:

1. 관리자 설정의 실험 기능에서 자동 답변을 명시적으로 켠다. 기본은 꺼짐이며 해당 세션에만 적용한다. 일반 사용자에게는 메뉴를 노출하지 않는다.
2. 기존 `flushUtterance()`의 확정 발화와 직전 대화 문맥을 판단 대상으로 삼는다. 미확정 글자가 바뀔 때마다 호출하지 않는다.
3. 발화 완결 여부, 사용자에게 요구된 답변인지, 이미 답변한 주제인지 판단한다. “물음표 포함” 규칙만으로 결정하지 않는다. “설명해 보세요” 같은 요청도 인식하고, 혼잣말·수사적 질문·발화 중간은 기다린다.
4. 확신이 충분하면 기존 강의·자료 문맥과 답변 렌더러를 활용해 짧은 힌트나 답변을 자동 생성한다. 짧은 핵심 2~3개를 먼저 보여주고 상세 설명은 펼칠 수 있게 하는 방향을 권장한다. 음성 출력은 첫 버전 범위에 넣지 않는다.
5. 같은 발화·질문 ID 중복 처리, 재연결 재전송, 여러 탭 동시 실행은 서버의 처리 기록/생성 잠금으로 막는다. 사용자가 직접 질문하면 우선 처리하며 자동 답변은 입력 중인 글이나 스크롤 위치를 바꾸지 않는다.

기존 `submitQuestion()`은 가상의 사용자 질문 말풍선을 만들고 최신 위치로 강제 이동한다. 자동 답변이 이를 그대로 호출하면 사용자가 입력한 질문처럼 기록되고 읽던 화면을 빼앗는다. 공통 전송·스트리밍 로직을 분리하고 `manual`/`proactive` 출처, 근거 발화 범위, 감지한 질문을 별도로 저장해야 한다. 별도 실험 지침을 사용해 면접 요청에도 “강의 조교” 지침이 무조건 적용되지 않게 한다.

가장 큰 불확실성은 답변 생성보다 **누가 누구에게 말했는지와 언제 끼어들어야 하는지**다. 방 안의 단일 마이크 전사만으로 역할을 완벽히 구분할 수는 없다. 온라인 면접의 상대방 소리와 본인 마이크가 분리되어 있으면 판단 근거가 좋아진다. 화자 분리 기능만으로 화자의 실명·역할까지 자동으로 아는 것은 아니다.

비용은 기존 STT를 중복 실행하지 않고 판단용 짧은 문맥과 실제 답변 생성분만 추가한다. 판단/생성 횟수, 실제 토큰, 지연, 불필요했던 답변 피드백을 기록하고 관리자용 시간당 예산을 둔다. 기존 일반 질문 횟수 제한만으로 자동 실행 비용을 관리하지 않는다. 초기 버전은 강의실을 열어 둔 동안 작동하며, 탭을 닫아도 동작하는 서버 실행은 별도 범위다.

검증: 직접 질문·간접 요청·수사적 질문·말 중간·자기 답변·중복 전사·빠른 후속 질문 사례를 평가한다. 비관리자 직접 API 호출 차단, 수동 질문 우선권, 모드 해제 후 생성 중단도 확인한다. 응답 지연은 발화 종료부터 첫 표시까지 측정하며 검증 전 초 단위 성능을 보장하지 않는다.

## 휴대폰을 마이크로 사용

추천 UX는 노트북의 **휴대폰 마이크 → QR 스캔 → 휴대폰에서 연결·마이크 허용**이다. 휴대폰에는 연결 상태·입력 레벨·중지 버튼만 두고 질문·자료·답변은 노트북에 둔다. 브라우저 마이크 권한은 사용자가 직접 허용해야 한다. 앱 설치나 같은 Wi-Fi를 제품 사용 조건으로 요구할 필요는 없다.

추천 경로:

`휴대폰 마이크 → 기존 Lecue STT 중계 → 인식 결과 저장 → 노트북의 같은 세션/질문 화면`

노트북에 오디오를 먼저 보내는 WebRTC 방식도 가능하지만, 이 경로에서는 STUN/TURN과 추가 음성 중계 구성을 도입하지 않아도 된다. 휴대폰만 음성 입력 연결을 소유하고 두 기기는 한 세션·한 크레딧 사용량을 공유한다. 녹음 한 시간을 두 기기에서 이중 차감하지 않도록 검증한다.

현재 코드에서 반드시 바꿀 부분:

- `workspace-client.tsx`의 `openSession()`은 복원 대상이 녹음 중이면 pause 요청을 보낸다. 지금 두 기기로 열면 다른 기기의 녹음을 멈출 수 있다. 단순 열람과 녹음 인계를 구분해야 한다.
- 실시간 인식 결과는 음성을 보낸 브라우저로만 돌아가며, 그 브라우저가 확정 문장을 저장한다. 현재 노트북에 다른 기기의 live 문장을 구독하는 경로는 없다. 초기에는 cursor 기반 증분 문장/상태 조회를 추가하고, 미확정 문장이 꼭 필요할 때 세션 범위 broadcast를 추가한다. 전체 세션을 매초 재조회하지 않는다.
- 녹음 상태·수업 시간·로컬 마이크 상태가 같은 hook에 결합돼 있다. 노트북 질문 시점과 “방금 그 말” 문맥은 원격 녹음의 시간·최신 발화를 기준으로 해야 한다.
- 노트북 종료 명령, 휴대폰 일시정지, 끊김·재연결, 녹음 기기 인계의 상태 전이를 서버에서 구분한다. 기존 사용자당 한 개의 활성 릴레이 연결 제한을 보존한다.

재로그인을 줄이려면 QR에 **짧은 유효기간의 일회용 연결 권한**을 담고, 교환 후 해당 세션의 마이크 전송·상태 확인만 허용한다. 기존 전체 로그인 토큰이나 공급자 API 키를 QR에 넣지 않는다. 첫 연결 후 링크는 재사용 불가, 녹음 종료·기기 해제 시 권한도 폐기한다. 일반 계정 권한과 분리된 페어링 API 및 서버 권한 검증이 추가로 필요하다. 더 작은 초기 실험은 휴대폰에도 같은 계정 로그인을 요구할 수 있지만 최종 UX로는 QR 전용 연결이 더 적합하다.

모바일 제약:

- HTTPS와 마이크 권한이 필요하다. [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- 첫 웹 버전은 휴대폰의 마이크 페이지를 열어 둔 상태를 지원 기준으로 삼는다. 기존 Wake Lock을 활용할 수 있지만 화면을 꺼 둔 상태, 다른 앱, 전화 수신에서도 계속 녹음된다고 약속하지 않는다. 화면 유지 요청은 배터리·시스템 상태에 따라 거절되거나 해제될 수 있다. [MDN Screen Wake Lock](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API)
- 화면 잠금·앱 전환·블루투스 연결 변경·Wi-Fi와 모바일망 전환을 실제 iPhone Safari와 Android Chrome에서 검증한다. 현재 30초 버퍼는 캡처 자체가 중단된 구간을 복원하지 못한다.
- 품질 향상은 휴대폰이라는 기기명보다 발화자와의 거리·배치·마이크 특성에 달렸다. 같은 위치에서 언제나 노트북보다 좋다는 보장은 없다. 잡음 억제·자동 게인·에코 제거 설정도 실물로 비교한다.

## 권장 구현 순서

1. 관리자 전용 자동 답변: 기존 녹음 입력으로 판단 품질부터 검증. 사용자 피드백으로 불필요한 개입을 줄인다.
2. 휴대폰 마이크: 전용 페이지·QR 연결·노트북 열람 모드·동기화·단일 과금 검증.
3. 두 기능 결합: 휴대폰 입력에서도 자동 답변의 시점·중복·복구·지연 확인. 장시간 녹음과 모바일 중단 시험을 통과한 뒤 일반 사용자 공개 여부를 정한다.
