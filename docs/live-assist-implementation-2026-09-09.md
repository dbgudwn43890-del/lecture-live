# 관리자 실시간 답변 구현

최신 자료·채팅 연결 변경은 [2026-09-10 기록](live-assist-context-2026-09-10.md)을 참고한다.
아래 최초 구현·진단의 배포 상태와 입력 문맥 범위는 당시 기록이다.

2026-09-09. 기존 검토 문서에서 제안했던 핵심 목록·펼치기 UI는 사용자의 후속 요청에 따라 적용하지 않는다. 대화에 바로 쓸 수 있는 짧고 구체적인 답변을 기존 채팅 화면에 표시한다.

## 사용 방법

지정된 관리자 계정으로 강의실에 로그인한 뒤 **설정 → 관리자 실험실 → 실시간 답변**을 켠다. 기존 마이크 또는 온라인 강의 입력을 시작하면 새로 들어오는 대화를 감지한다. 기본은 꺼짐이다. 표시된 상태 줄의 **끄기**로 중단할 수 있다.

다른 계정에는 설정이 보이지 않는다. API도 Supabase가 검증한 이메일과 이메일 인증 완료 여부, 강의 소유권, 녹음 상태, 크레딧을 다시 검사한다. 클라이언트에서 UI 값을 바꾸어도 권한이 생기지 않는다.

## 동작

- 기존 WebSocket 전사의 확정 문장과 중간 전사를 사용한다. 전체 스크립트를 주기적으로 재조회하거나 STT를 이중 실행하지 않는다.
- 새로운 내용이 잠시 안정되면 최근 문맥을 평가한다. 모델 요청 한 번 안에서 기다릴지 답할지 판단하고, 답변이면 즉시 스트리밍한다. 판단 표식은 사용자에게 표시하지 않는다.
- AI 사용이 허용된 면접·토론·일반 대화·강의를 대상으로 한다. 실제 답, 풀이, 바로 쓸 표현과 구체적 예시를 제공한다. 개인 경험을 알 수 없을 때는 만들어낸 이력을 사실처럼 쓰지 않고 가정한 예시임을 밝힌다.
- 미완성 발화·수사적 질문·이미 답한 내용은 기다린다. 중간 전사와 확정 전사의 중복 및 같은 내용의 재전송을 억제한다.
- 직접 입력하는 질문과 초안은 유지한다. 자동 답변은 사람이 보낸 가짜 질문 말풍선을 만들지 않는다. 기존 스크롤 동작을 사용해 사용자가 위로 이동하면 화면을 끌어내리지 않는다.
- 직접 "방금 답변을 더 설명해 줘"라고 물으면 최근 자동 답변 최대 3개도 참고한다. 각 2,000자로 제한하며, 관리자 권한을 서버에서 다시 확인한다.
- 모드를 끄거나 수업을 바꾸거나 화면을 떠나면 해당 자동 요청을 취소한다. 현재 실험의 자동 답변은 화면 내 기록이며 일반 질문처럼 서버에 저장하거나 복습노트에 넣지 않는다.

## 비용·검증 범위

서버는 최근 전사 6,000자와 최근 자동 답변 최대 6개만 받는다. 각 이전 문맥도 길이를 제한한다. 모델은 기존 플랫폼의 `gpt-5.6-luna`, 출력 상한 650 tokens, 외부 검색 없음이다. 관리자 한 계정에 15초당 8회·시간당 900회 상한을 둔다. 사용량 로그에는 토큰 수, 응답 판단(wait/answer), 판단·첫 본문·사전 검사·전체 처리 시간, 실패·취소 여부만 남기며 전사·답변·계정 이메일은 남기지 않는다.

정해진 몇 초 이내 응답을 보장하지는 않는다. 음성 인식·발화 끝 판단·모델 응답 속도에 따라 실제 지연이 달라진다. 하나의 마이크로는 화자의 역할이나 질문 의도를 항상 정확하게 알 수 없다.

## 검증 결과

- 전체 테스트 524개 통과, 타입 검사 및 diff 검사 통과.
- 관리자/다른 계정/미인증 계정, 세션 소유권, 사용량 제한, PCM 선결제 구간, 분할 스트림·취소·중복·짧은 질문·후속 질문·오류 후 복구를 모의 응답으로 검증했다.
- 실제 로컬 `/api/live-assist`에 로그인 없이 요청해 HTTP 401 차단을 확인했다.
- Chrome에서 관리자 설정 노출·스위치 동작을 확인하고 데스크톱과 390px 모바일 폭을 직접 확인했다. Impeccable 감지 결과 0건.
- 실제 마이크 입력 및 OpenAI 모델 품질·응답 지연 평가는 아직 수행하지 않았다. 가상 대화 3건의 유료 API 평가는 사용자 승인 질문이 대기 중이며, 이 작업에서 유료 호출은 하지 않았다.

현재 로컬 구현 상태이며 이 변경사항은 운영에 배포하지 않았다. 휴대폰 마이크는 별도 입력·기기 동기화 작업으로 남겨 둔다.

## 2026-09-10: 반복해야 답하는 현상 진단

사용자가 실제 녹음은 동작하지만 같은 질문을 약 10번 반복해야 자동 답변이 나온다고 보고했다. 실제 대화 내용은 읽거나 새 유료 평가에 전송하지 않았다. 기존 로컬 서버의 사용량 로그 17건은 모두 HTTP 200이었다. 모델 구간 전체 처리 시간은 16건에서 약 1.0~3.0초, 1건에서 약 7초였다. 이는 음성 발화 종료부터 첫 유효 답변까지의 시간이 아니다. 기존 로그에는 WAIT/ANSWER가 없으므로 토큰 수만으로 모델의 답변 보류 여부나 이 사용자의 전체 실패 원인을 단정할 수 없다.

합성 받아쓰기와 모의 모델 응답으로 다음 클라이언트 결함을 재현했다.

- ‘현재가치가 무엇인지’에 WAIT를 받은 뒤 ‘설명해줘.’가 추가돼도, 새 글자가 8자 미만이라 재요청이 없었다. 문장이 확정된 뒤 20초가 지나도 그대로였다.
- ‘설명해줘.’처럼 짧고 정상적인 요청은 처음부터 전송되지 않았다.

최소 변경량을 8자에서 2자로 낮추고 실제 답변 여부는 모델이 판단하도록 수정했다. 한국어·영어·스페인어·일본어의 짧은 요청, WAIT 후 짧은 완성 문장의 재판단, 같은 확정 문장으로 60초 동안 추가 요청이 생기지 않음을 검증했다. 600ms 안정화, 요청 간 최소 1.5초, 연속 발화 대기 상한 2.5초, 서버 비용 한도는 유지한다. 짧은 추가 발화도 검토하므로 실제 요청 수가 이전보다 늘 수 있으나 새 상한이나 상시 재조회는 추가하지 않았다.

답변 보류와 생성 지연을 구분하기 위한 내용 없는 진단 항목을 추가했다. 관련 테스트 32개, 타입 검사와 diff 검사 통과. 새 유료 API 호출·모델 변경·운영 배포는 하지 않았다.

남은 한계: 텍스트가 전혀 달라지지 않고 중간 전사가 확정으로만 바뀌는 경우에는 WAIT 이후 재판단하지 않는다. 진행 중 모델 요청 뒤의 새 발화는 그 요청 완료까지 대기한다. 화자 구분 없는 음성에서 수사적 질문과 실제 답변 요청의 의도 판정도 정확도를 따로 측정해야 한다. 이번 수정으로 실제 대화의 응답 속도·감지율이 충분해졌다고 검증한 것은 아니다.

권장 판단 기준은 관리자 실험 상태에서 발화 종료부터 첫 유효 답변까지의 시간, 한 번 말한 명확한 질문의 응답률, 불필요한 개입 횟수를 함께 측정하는 것이다. 목표로 3초 안팎의 첫 유효 답변을 둘 수 있으나 보장값은 아니다. 이를 확인하기 전에 비용이 드는 음성 모델 전환이나 공개 기능 확대를 결정하지 않는다.
