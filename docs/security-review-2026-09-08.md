## S1. 강의·자료 연결의 소유권 검사 누락

위치:

- `supabase/migrations/20260902040000_lecture_notes.sql:19`
- `supabase/migrations/20260825000000_optional_classrooms.sql:32`
- `supabase/migrations/20260831030000_allow_material_chunk_insert.sql:4`
- `supabase/migrations/20260822010000_classrooms.sql:138`
- `app/api/ask/route.ts:407`

`lecture_notes`, `lecture_chunks`, `material_chunks`는 작성 행의 `user_id`가 본인인지만 검사한다. 연결한 `session_id` 또는 `document_id`도 같은 사용자의 것인지 검사하지 않는다. 운영 DB의 정책과 authenticated INSERT 권한이 실제로 이 상태다.

확인한 영향:

1. **복습노트 생성 방해 — 로컬 DB 재현.** 다른 사용자의 강의 UUID를 아는 사람이 본인 소유의 노트를 그 강의에 연결할 수 있다. `session_id`가 유일해야 하므로 정상 사용자의 노트 생성 upsert가 RLS 충돌로 실패한다. 다른 사용자의 강의 SELECT는 차단돼도 이 연결은 허용됐다.
2. **강의 제목 노출 — 로컬 DB 재현.** 본인 청크를 다른 사용자의 강의에 연결하면 서비스 전용 검색 함수가 연결된 강의의 제목을 반환한다. 함수가 청크 소유자만 검사하고 조인한 강의 소유자를 재검사하지 않는다. 전체 강의 본문 유출을 재현한 것은 아니다.
3. **자료 문맥 오염 — 정적 확인.** 본인 청크를 다른 사용자의 자료에 연결할 수 있고, `/api/ask`의 자료 개요 조회는 서비스 권한으로 `document_id`만 필터링한다. 해당 청크가 첫 페이지로 선택되는 조건에서는 다른 사용자의 답변 문맥에 섞일 수 있다. 실제 모델 유도·유출은 시험하지 않았다.

전제: 피해 강의/자료 UUID를 알아야 한다. UUID 수집이나 열거 가능성을 입증하지 않았다. 임의의 모든 사용자 데이터를 읽을 수 있다는 뜻은 아니다.

운영의 세 테이블에서 상위 자료와 소유자가 다른 행은 **각각 0건**이었다. 현재 이상 행이 없다는 뜻이며 과거 침해 부재의 증거는 아니다.

수정: 하위 행 작성 정책에 상위 행의 소유권 검사를 추가하고, 브라우저가 쓸 필요가 없는 생성 결과는 서비스 전용 쓰기로 제한한다. 서비스 권한 조회에도 `user_id` 및 상위 소유권 조건을 추가한다. 기존 이상 행 검사를 포함한 migration으로 적용한다.

완료 기준: 합성 사용자 A가 B의 강의·자료를 참조하는 INSERT/UPDATE는 모두 실패하고, A/B의 정상 생성·검색·이동은 유지돼야 한다. [Supabase RLS 원칙](https://supabase.com/docs/guides/database/postgres/row-level-security).

## S2. STT 토큰 발급 후 비용 통제 누락

위치: `app/api/deepgram-token/route.ts:86`, `:140`, 클라이언트 레코더의 주기적 차감 호출.

발급 시 인증·동의·잔액·공유 요청 제한과 최초 1분 차감은 확인한다. 그러나 발급된 공급자 토큰은 브라우저가 직접 사용하며, 이후 크레딧 차감과 스트림 종료는 정상 클라이언트의 동작에 의존한다. Lecue가 스트림을 직접 소유하거나 공급자 측 사용 시간을 강제하지 않는다.

Deepgram의 30초 TTL은 **연결을 시작할 수 있는 시간**이며 이미 열린 연결을 30초 뒤 종료하지 않는다. 공식 문서는 임시 토큰의 STT 외 API 사용도 설명한다. 코드의 `scopes: ["listen"]`만으로 실제 권한이 STT에 제한된다고 간주해서는 안 된다. 이번에는 발급 토큰으로 유료 API나 다른 기능을 호출하지 않았다. [Deepgram 임시 토큰 공식 설명](https://developers.deepgram.com/guides/fundamentals/token-based-authentication).

Soniox 발급 요청에는 공급자가 지원하는 `single_use`, `max_session_duration_seconds`가 없다. [Soniox 임시 키 설정](https://soniox.com/docs/api-reference/auth/create_temporary_api_key).

영향: 정상 UI의 차감/종료 절차를 따르지 않는 클라이언트가 Lecue의 크레딧 예산보다 많은 공급자 리소스를 사용할 여지가 있다. 짧은 TTL과 분당 발급 제한은 이 문제의 충분한 방어가 아니다. 실제 피해액과 공급자 계정의 최종 지출 상한은 확인하지 않았다.

수정: 공급자가 제공하는 단일 연결·최대 시간 제한을 적용하고, 사용자별 동시 연결과 비용을 서버에서 예약·정산한다. Deepgram처럼 클라이언트의 직접 연결만으로 강제 종료를 보장하기 어려운 경우 서버가 연결을 통제하는 구조를 검토한다. 공급자 프로젝트 지출 상한은 별도 방어로 둔다.

완료 기준: 클라이언트가 차감 요청을 보내지 않아도 예약한 사용량을 초과해 계속 처리할 수 없어야 한다. 동일 토큰/사용자의 동시 연결도 한도 안에서 통제돼야 한다.

## S3. 파일 변환 비용을 실제 길이보다 적게 확인함

위치: `app/api/lecture-audio/route.ts:194`, `:285`.

업로드 전 필요 크레딧은 사용자가 신고한 길이와 파일 크기 추정값으로 계산한다. 압축률·샘플레이트가 다르면 파일 크기는 정확한 길이 보장이 되지 않는다. 잔액을 조회만 하고 예약하지 않아 여러 요청이 같은 잔액을 동시에 사용할 수도 있다.

실제 라우트에 유효한 **180초 WAV**, 신고 길이 1초, 잔액 1크레딧을 넣은 로컬 테스트에서 **202로 접수되고 공급자 처리 요청 단계까지 진행**했다. 네트워크 호출은 모두 가로챘으며 실제 공급자 과금은 없었다. 콜백에서 결과를 유료 분량만큼 잘라도 이미 시작한 전체 파일 처리 비용을 예방할 수 없다.

수정: 서버가 파일 헤더/미디어 분석으로 길이를 검증하고, 최대 길이·형식·크기를 함께 제한한다. 공급자 요청 전에 원자적으로 크레딧/비용 예산을 예약하고 실패 시 해제한다. 사용자별 대기·진행 중 작업 수도 제한한다.

완료 기준: 과소 신고와 동시 업로드에서 잔액보다 큰 작업은 공급자 호출 이전에 거부된다. 정상 파일의 오류·취소에는 예약이 정확히 복원된다.

## S4. Storage 직접 쓰기가 앱 제한을 거치지 않음

위치: `supabase/migrations/20260830010000_lecture_audio_uploads.sql:69`, `supabase/migrations/20260828040000_material_files.sql`.

운영의 `lecture_audio_owner`, `materials_owner`는 본인 UUID 폴더 안에서 authenticated 사용자에게 ALL 작업을 허용한다. 앱의 업로드 API를 통하지 않고 Storage API를 직접 사용하면 동의·크레딧·파일 개수·일일 사용량 검사와 추적 행 생성이 적용되지 않는다.

운영 버킷은 비공개이며 다른 사용자 폴더 접근을 허용하는 문제는 아니다. 개별 파일 상한은 audio 1GB, materials 20MB다. 로컬 정책 검증에서는 `uploads` 행 없이 본인 폴더의 객체 등록이 허용됐다. 운영에 실제 파일을 올리는 검증은 하지 않았다.

현재 Supabase Free 조직이므로 특히 저장 공간 소진과 서비스 가용성 문제가 중요하다. 유료 전환 시에는 추가 비용 위험도 커진다. 요금제의 총량 제한이 앱의 사용자별 공정한 한도를 대신하지는 않는다.

수정: 브라우저 직접 INSERT/UPDATE 권한을 제거하거나, 서버가 예산을 예약하고 허용한 경로에만 업로드할 수 있게 한다. 모든 업로드의 추적 행과 완료 처리를 보장하고 추적 없는 객체를 정기적으로 검사한다. [Supabase Storage 접근 제어](https://supabase.com/docs/guides/storage/security/access-control).

완료 기준: 승인된 업로드 없이 Storage를 직접 쓰는 요청은 실패한다. 정상 PDF/음성 업로드·열람·삭제는 유지된다.

## S5. 강의 완료·재색인에 외부 API 예산 관문이 없음

위치: `app/api/lecture-sessions/route.ts:606`, `:673`, `:709`.

완료 요청에서 클라이언트의 스크립트를 저장한 뒤 크레딧 차감 RPC의 `error`만 확인한다. 응답의 `allowed: false`를 처리하지 않고 임베딩으로 진행한다. 세션 생성 자체에도 잔액 관문이 없다. 따라서 잔액 없는 계정이 새 세션에 텍스트를 제출해 외부 임베딩 처리를 발생시키는 경로가 남는다.

동일 세션의 완료 재전송은 상태 조건으로 막지만 새 세션 생성까지 막는 것은 아니다. 또한 본인 `lecture_chunks` DELETE 권한과 누락 청크 재색인 기능을 함께 보면, 재색인에도 별도 작업 예산이 필요하다. 요청 빈도와 입력 크기 제한은 존재하므로 무제한이라고 표현하지 않는다.

수정: 사용자의 기록 보존과 유료 색인 실행을 분리한다. 잔액 부족이어도 기록은 보존하되, 서버의 원자적 예산 승인 없이는 새 유료 작업을 실행하지 않는다. 재색인에는 작업별 멱등성, 사용자별 일일 비용 및 서버 전용 청크 쓰기를 적용한다. [OWASP 외부 리소스 비용 통제](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/).

완료 기준: 잔액 없는 새 세션·완료·복구·재색인 요청에서 공급자 호출이 발생하지 않으며 정상 기록은 소실되지 않는다.

## S6. 삭제 완료로 표시한 뒤 파일이 남을 수 있음

위치: `app/api/lecture-audio/route.ts:61`, `app/api/lecture-audio/callback/route.ts:55`, `:191`, `app/api/lecture-sessions/route.ts:534`, `app/api/materials/route.ts:354`.

- 음성 만료 청소는 사용자가 업로드 상태를 조회할 때만 실행된다. 사용자가 돌아오지 않으면 24시간 삭제가 보장되지 않는다.
- 일부 경로는 Storage 삭제 실패에도 DB의 `object_key`를 지우고 `deleted_at`을 기록한다. 재시도할 연결 정보가 사라진다.
- 처리 중인 세션 삭제는 uploads 행을 연쇄 삭제하지만 음성 객체 경로를 먼저 수집하지 않는다. 이후 콜백도 해당 행을 찾을 수 없다.
- PDF 삭제는 DB 행을 먼저 지운 뒤 Storage 삭제에 실패하면 로그만 남긴다.

운영 Vercel cron 정의는 **0개**, DB `pg_cron` 확장은 없다. 이번 운영 집계에서 추적 없는 audio/material 객체와 삭제 기한이 지난 추적 audio는 **모두 0건**이었다. 현재 잔존 파일이 발견된 것이 아니라 실패 시 보관·삭제 약속이 깨지는 경로다. 별도 외부 예약 작업은 확인되지 않았다.

수정: 삭제 대상 경로를 durable queue에 남기고 성공 후 완료 처리한다. 세션 삭제 전 경로를 보존하고, 독립된 주기 작업으로 재시도·고아 객체 검사를 수행한다. Storage 삭제와 개인정보 처리방침의 실제 보관 기간을 일치시킨다.

완료 기준: Storage 일시 오류·사용자 이탈·변환 중 세션 삭제를 포함한 테스트에서 파일이 재시도 후 삭제되고, 삭제 전에는 추적 정보가 유지된다.

## S7. 다이어그램의 자동 외부 요청

위치: `app/lib/lecture-note-context.ts:136`, `app/classroom/lecture-note.tsx:344`.

Mermaid 검증은 다이어그램 종류만 검사하고 외부 이미지 구문을 허용한다. 설치된 Mermaid 11.17.2의 `securityLevel: "strict"`에서도 이미지 노드를 렌더링할 때 외부 요청이 발생했다. 다이어그램이 닫힌 `<details>` 안에 있어도 요청했다. 앱의 실제 검증 함수를 통과시킨 뒤 브라우저 요청을 가로채 확인했으며 외부 전송은 하지 않았다.

영향: 외부 서버가 사용자의 IP와 열람 사실을 알 수 있다. 모델이 비공개 강의 내용을 URL에 넣으면 해당 문자열도 전송될 수 있다. 이를 위해서는 모델이 해당 구문을 생성하도록 영향을 받아야 하며, 그 전체 유도 과정은 검증하지 않았다. 임의 JavaScript 실행이나 쿠키 탈취를 확인한 것은 아니다.

운영 CSP가 없어 이 요청을 별도로 막지 않는다. [Mermaid 이미지 노드](https://mermaid.js.org/syntax/flowchart.html?id=flowcharts-basic-syntax)는 정상 라이브러리 기능이므로 앱의 신뢰 경계에서 제한해야 한다.

수정: `mermaid.render()` 전에 외부 리소스 구문을 차단하거나, 네트워크 제한이 적용된 별도 환경에서 렌더링한다. 렌더링 이후 SVG만 정화하면 최초 요청은 이미 발생한 뒤다. CSP는 Paddle·STT·Supabase 연결을 확인하면서 단계적으로 적용한다.

완료 기준: 악의적인 모델 출력이 들어와도 외부 이미지 요청이 전혀 발생하지 않고 일반 다이어그램은 정상 표시된다.

## 운영 설정에서 추가로 확인한 위험

### 백업과 복구 — 높은 운영 우선순위

실제 Supabase 화면에 **Free Plan does not include project backups**라고 표시된다. 프로젝트 개요도 No backups다. 저장소에서 독립된 정기 백업 작업은 찾지 못했다. 소스 코드와 migration만으로 사용자의 강의·결제 잔액을 복구할 수는 없다.

유료 백업을 사용하거나 암호화된 외부 정기 백업과 복원 시험을 마련해야 한다. 어느 방식이든 보존 기간·복구 가능한 시점·복구 소요 시간을 정해야 한다. 자동 백업 기능 부재는 확인했지만 사용자가 따로 보관한 백업의 존재까지 부정하는 것은 아니다. 요금제 변경은 이번 검토에서 하지 않았다.

### 가입 남용과 계정 보호 — 설정 보완

운영 설정:

- 이메일·Google 로그인 활성, **Confirm email 활성**, 익명 로그인·수동 계정 연결 비활성.
- CAPTCHA 비활성. 유출 비밀번호 차단 비활성(대시보드에서 Pro 이상 기능으로 표시).
- Secure email change 활성. Secure password change와 Require current password when updating은 비활성.
- 가입/로그인 IP 제한 30회/5분, 토큰 확인 30회/5분, 토큰 갱신 150회/5분.
- Email OTP 만료 3,600초, 길이 8자리. 최소 비밀번호 길이 입력은 빈 값으로 표시돼 실제 기본값까지 확인한 것으로 기록하지 않는다.

이메일 인증만으로 다중 무료 계정 생성이나 분산된 로그인 시도를 모두 막지는 못한다. 정상 가입 UX를 해치지 않도록 CAPTCHA·위험 신호·무료 지급 제한을 조합하고, 비밀번호 변경에는 최근 인증 또는 현재 비밀번호 확인을 검토한다. 설정 비활성만으로 계정 탈취가 성공했다고 판단하지 않는다.

### 비밀키와 환경 분리 — 확인이 남은 항목

- 이메일 로그인 작업 기록에 OpenAI 키가 이전 도구 출력에 나타나 교체를 권고한 내용이 있다. **2026-09-08 사용자 답변으로 교체 완료를 확인**했다. 공급자 대시보드의 폐기 이력까지 재검증한 것은 아니며, 이번 검토에서는 키를 출력하지 않았다.
- Vercel에서 OpenAI, Deepgram, Supabase, Cloudflare 관련 변수 이름이 Production과 Preview 양쪽 대상으로 등록돼 있음을 확인했다. 값은 읽지 않았으므로 동일 키인지 단정하지 않는다. 테스트 환경은 별도 DB·제한된 API 프로젝트·예산으로 분리해야 한다.
- Vercel preview/deployment 보호는 `all_except_custom_domains`, Git fork 보호는 활성이다. 방화벽의 active custom config 조회는 404를 반환했다. 사용자 정의 규칙을 확인하지 못했다는 뜻이며 Vercel의 기본 플랫폼 보호가 없다는 뜻은 아니다.
- OpenAI·Deepgram·Soniox의 계정별 지출 상한, 키별 실제 권한, Cloudflare 계정 보호, 관리자 계정의 MFA·복구 수단은 확인하지 않았다. 앱의 비용 통제를 보완할 별도 운영 점검 항목이다.

## 확인된 정상 보호 및 과장하지 않은 항목

- 운영 public 테이블 22개 모두 RLS 활성. 관련 파일 버킷 비공개.
- Supabase Security Advisor: 오류 0, 경고 10. 경고 중 9개는 authenticated 사용자의 SECURITY DEFINER 실행 허용이다. 실제 함수 본문에서 `auth.uid()` 소유권 검사·고정 search_path를 확인했고 anon EXECUTE는 모두 차단돼 있었다. **9개를 취약점 9건으로 세지 않았다.**
- 검색·결제 적용·비밀키 관련 서비스 함수는 실제 운영에서 anon/authenticated EXECUTE가 차단돼 있다. public/extensions 스키마의 CREATE도 두 역할 모두 차단돼 있다.
- Paddle Live 웹훅은 `https://www.lecue.app/api/billing/webhook`, Active, 11개 이벤트 구독. 기존 `transaction.completed` 전달 1건이 1회 시도로 Delivered 상태인 것을 확인했다. 새로운 거래나 이벤트 재전송은 하지 않았다. 11개 이벤트의 상세 목록과 모든 환불·구독 변경의 운영 성공까지 검증한 것은 아니다.
- 코드에서 원문 HMAC 서명·시간 허용 범위·상수 시간 비교, 서버 주문/가격/고객 연결, 원자적 결제 반영과 중복 처리를 확인했다. 관련 기존 테스트는 통과했다.
- 운영의 비인증 `/api/credits`, `/api/llm-credentials`, `/api/lecture-sessions`, `/api/classrooms`는 401, `/api/admin`은 403.
- HTTP→HTTPS, apex→www는 308. HSTS/includeSubDomains, DENY, nosniff 적용. 홈페이지는 private/no-store, 정적 JS는 immutable. 외부 Origin을 보낸 인증 API 응답에서 광범위 CORS 허용을 관찰하지 않았다.
- `/.env`, `/.git/HEAD`는 로그인으로 307 이동했고 공개 파일 노출은 관찰되지 않았다. 발견된 JS 한 개의 source map 요청은 403이었다. 모든 파일 또는 인증 후 접근을 전수 검사한 것은 아니다.
- 일반 답변은 raw HTML·이미지·위험 태그 제한을 유지하고 KaTeX는 trust=false다. CSP 부재만으로 XSS라고 판정하지 않았다.

### Next.js 공식 보안 공지에 대한 운영 판정

설치된 Next 16.3.2, Sharp의 libheif 1.23.1은 [Next 공식 AVIF 공지](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4)의 영향 버전이다. 그러나 **Vercel은 관리형 Image Optimization의 AVIF 최적화 중단과 Linux 런타임으로 해당 8월 취약점들을 보호한다고 명시**한다. 따라서 현재 Vercel 운영의 Critical RCE로 계산하지 않는다. 자체 호스팅·환경 이전을 대비한 Next 16.3.3 이상 갱신은 의존성 유지보수로 권고한다. [Vercel 공식 보호 조치](https://vercel.com/changelog/nextjs-august-2026-security-release).
