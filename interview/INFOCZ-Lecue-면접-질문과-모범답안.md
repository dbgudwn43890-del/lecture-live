# INFOCZ FDE 면접: Lecue 질문과 모범답안

작성 기준: 2026-09-09의 로컬 코드·프로젝트 기록, 지원자가 제공한 채용 이메일과 회사 분석.

이 문서는 실제 기출이 아니라, 이메일의 평가 항목인 **문제 정의 → 정보·가설 설정 → 구현 → 검증**에 맞춘 예상 질문 72개와 실습 질문 8개다. 회사 제품·전형 정보는 이번에 별도로 재조사하지 않았다.

답안의 1인칭 표현은 연습용 초안이다. 코드가 존재한다고 지원자가 직접 설계·구현했다는 사실까지 확인되는 것은 아니다. 직접 판단한 일, AI와 함께 수행한 일, 아직 이해하거나 검증하지 못한 일을 구분해서 말한다. 아래의 ‘앞으로 하겠습니다’는 현재 구현된 기능이나 과거 성과가 아니다.

지원자가 확인한 실적: **약 5일간 개발, 무료 이용자 약 20~30명, 유료 결제 1건. 현재 무료 기간 종료 후 유료 전환을 높이기 위해 지속적으로 유지보수 중이다.** 결제 1건을 유료 사용자 1명이나 반복 매출로 바꾸어 말하지 않는다. 무료 이용자 전원이 체험을 마친 것이 아니므로 이를 분모로 확정 전환율을 산출하지 않는다. 개발 기간 5일과 후속 유지보수 기간도 구분한다.

현재 프로젝트를 근거로 바로 말할 수 있는 답안을 아래에 작성했다. 개인의 개발 동기, 협업 갈등이나 특정 테스트를 본인이 수동으로 수행했는지처럼 기록으로 확정할 수 없는 내용은 지어내지 않았다.

## 먼저 익힐 답변 구조

첫 답변은 30~60초로 한다. **해결하려던 문제 → 선택과 이유 → 구체적 근거 → 한계**를 말하고, 추가 질문이 오면 구현 세부로 들어간다. 장애 사례는 90초까지 늘려도 좋다.

가장 먼저 연습할 질문: 1, 3, 5, 8, 13, 14, 23, 24, 33, 39, 43, 48, 53, 56, 64.

숫자는 그 의미까지 기억한다. 60,000은 자료 문맥의 **문자 수 예산**이지 토큰 수가 아니다. 30초 버퍼는 모든 장애의 무손실 복구 보장이 아니다. 483개 테스트 통과는 해당 수정 당시 기록이고, 이번 문서 작성에서 재실행한 결과가 아니다.

## A. 제품·문제 정의·본인 기여

### 1. Lecue를 1분 안에 소개해 주세요.

**모범답안:** “Lecue는 강의를 실시간으로 전사하고 현재 강의와 첨부 자료를 바탕으로 질문에 답하는 학습 서비스입니다. 약 5일간 개발했고, 현재 무료 이용자가 약 20~30명이며 유료 결제도 1건 발생했습니다. 지금은 무료 기간이 끝난 뒤에도 계속 쓸 이유를 만들기 위해 유지보수하고 있습니다. 특히 자료를 올렸는데 답변이 내용을 못 찾는 문제와 음성 연결·누락 문제처럼 핵심 사용 경험을 해치는 부분을 개선하고 있습니다. 빠르게 만드는 것에서 끝내지 않고 실제 사용과 유료 전환까지 이어가는 것이 이 프로젝트의 현재 과제입니다.”

**꼬리질문:** 가장 중요한 기능 하나는? → 진행 중인 강의의 맥락을 유지한 질문·답변이라고 설명하고 2번으로 연결한다.

### 2. 정확히 누구의 어떤 문제인가요?

**모범답안:** “우선 대상으로 삼은 상황은 강의를 따라가다 특정 개념이나 방금 설명을 놓친 학생입니다. 불편을 ‘녹음이 필요하다’보다 ‘놓친 부분을 확인하면서도 현재 강의로 빨리 돌아오고 싶다’로 정의했습니다. 따라서 전사량보다 질문 후 강의로 복귀하는 시간과 추가 설명의 유용성이 더 중요한 성공 기준입니다. 이 정의가 실제 사용자에게 맞는지는 인터뷰와 사용 기록으로 검증해야 합니다.”

### 3. ChatGPT에 자료를 올리는 것과 무엇이 다른가요?

**모범답안:** “제가 집중한 차이는 실시간 강의 흐름과 맥락 연결입니다. 사용자가 방금 들은 내용을 매번 복사하지 않아도 전사, 최근 문답, 첨부 자료와 관련 과거 수업을 함께 활용합니다. ‘방금 놓쳤어요’ 같은 요청과 복습 노트도 같은 세션 안에서 이어집니다. 다만 일반 AI 서비스보다 학습 효과가 높다는 비교 실험은 아직 제시할 수 없고, 현재 차별점은 제품 흐름과 맥락 구성에 있습니다.”

### 4. 이 문제가 있다는 것을 어떻게 확인했나요?

**모범답안:** “현재 무료 이용자 약 20~30명이 있다는 점은 실제 사용 단계에 들어갔다는 근거입니다. 다만 가입·사용 자체가 학습 문제 해결의 증거는 아니므로, 어떤 상황에서 쓰고 어디에서 이용을 멈추는지 확인해야 합니다. 지금은 자료를 못 찾거나 음성이 누락되는 등 핵심 흐름의 문제를 개선하며 무료 기간 이후에도 사용할 가치를 만드는 데 집중하고 있습니다. 체계적인 사용자 인터뷰나 학습 효과 실험까지 완료했다고 말하지는 않겠습니다.”

### 5. 본인이 직접 한 일은 무엇인가요?

**모범답안:** “저는 Lecue를 약 5일간 빌드했고, 현재 실제 무료 이용자와 유료 결제가 있는 제품으로 계속 유지보수하고 있습니다. 제 경험을 설명할 때는 코드 작성량보다 제품의 문제를 어떻게 정의하고 개선했는지에 초점을 두겠습니다. 예를 들어 PDF 업로드 성공과 답변에 자료가 전달되는 상태를 구분하고, 음성 누락을 연결·버퍼·저장 단계로 나누어 다루는 것이 중요했습니다. AI 도움을 포함한 개발 과정과 별개로, 면접에서는 현재 구조의 선택 이유와 한계를 설명할 수 있는 범위를 명확히 보여드리겠습니다.”

**꼬리질문:** 지금 코드 없이 구현할 수 있나요? → 아래 실습의 중복 제거·청킹·오디오 시간 계산부터 직접 구현해 보여준다. AI 없이 전체 제품을 작성했다고 주장하지 않는다.

### 6. MVP 범위는 어떻게 정했나요?

**모범답안:** “핵심 흐름을 강의 입력, 전사, 질문, 답변 확인으로 잡겠습니다. 결제나 복습 확장은 핵심 사용성이 확인된 다음 단계로 평가할 수 있습니다. 현재 구현 범위는 인증·결제·복습까지 넓지만, 다시 검증한다면 한 과목과 한 입력 방식에서 실제로 학습자가 따라오는 데 도움이 되는지부터 보겠습니다.”

**주의:** 실제 개발 순서를 확인하지 않았으므로 이 답안은 ‘다시 한다면’의 판단이다.

### 7. 가장 어려웠던 문제 하나만 꼽는다면요?

**모범답안:** “기술 문제가 사용자에게는 하나의 ‘안 된다’로 보인다는 점입니다. PDF를 올렸는데 답변이 자료를 못 찾는 사례에서 업로드, 텍스트 추출, 색인, 검색, 문맥 전달을 분리해서 확인해야 했습니다. 검색 실패를 자료가 없는 상태로 취급하는 것이 핵심 문제였고, 실제 저장 텍스트의 조회 상태와 포함 범위를 답변 모델에 전달하도록 개선한 사례를 가장 자세히 설명할 수 있습니다.”

**연결:** 13~16번을 연속으로 연습한다. 직접 수행한 사례인지 먼저 확인한다.

### 8. Lecue 경험이 INFOCZ FDE와 어떻게 연결되나요?

**모범답안:** “보내주신 이메일에서 문제를 정의하고 필요한 정보와 가설을 설정하는 과정을 중요하게 본다고 이해했습니다. Lecue에서도 ‘AI가 답을 못한다’는 현상을 바로 모델 문제로 결론내리지 않고, 입력과 데이터 연결, 검색, 생성 단계를 나누어 확인하는 접근이 필요했습니다. 산업 데이터 경험과 같다고 말할 수는 없지만, 모호한 사용자 문제를 재현 가능한 기술 문제로 바꾸고 작동 여부를 검증하는 방식은 FDE 업무에 연결된다고 생각합니다.”

## B. 전체 구조·데이터·검색

### 9. 전체 아키텍처를 설명해 주세요.

**모범답안:** “브라우저는 입력 캡처와 전사·질문 화면을 담당하고, Next.js 서버는 인증, 문맥 조회, AI 호출과 저장을 처리합니다. Supabase의 Auth, Postgres, Storage를 쓰고, 실시간 음성은 일회용 티켓으로 Cloudflare Worker에 연결해 STT 공급자와 중계합니다. 결제는 Paddle 웹훅을 서버에서 검증해 DB에 반영합니다. 사용자 화면에서 보이는 상태와 비용·권한을 확정하는 서버 상태를 구분한 구조입니다.”

**화이트보드:** 브라우저 → Worker → STT / 브라우저 → Next.js → DB·LLM / Paddle → 검증 웹훅 → DB.

### 10. 왜 Next.js, TypeScript, Supabase인가요?

**모범답안:** “이 프로젝트에서는 화면과 서버 API를 함께 관리하고, 인증·저장소·관계형 데이터 기능을 빠르게 연결하는 구성이 적합합니다. TypeScript는 입력과 상태의 형태를 표현하는 데 도움이 되지만 런타임 검증을 대신하지 않으므로 API에서도 값을 확인합니다. Supabase를 사용해도 소유권 모델과 서비스 권한은 직접 설계해야 합니다. 최초 선택의 개인적 이유는 [실제 이유]였고, 이 설명은 현재 구조에서의 장단점입니다.”

**근거:** 현재 `package.json`의 Next.js는 16.3.3이다. README의 15와 혼동하지 않는다.

### 11. 데이터를 어떻게 모델링했나요?

**모범답안:** “사용자 아래에 강의실과 수업 세션이 있고, 세션에는 전사 구간, 질문·답변, 첨부 자료와 요약·노트가 연결됩니다. 자료는 문서 메타데이터와 검색할 텍스트 조각으로 구분합니다. 시간과 페이지 정보를 보존해야 답변의 근거로 돌아갈 수 있습니다. 또 자식 데이터가 연결된 부모의 소유자와 일치하도록 DB 제약을 적용하는 것이 중요합니다.”

### 12. 질문 한 번이 들어오면 어떤 일이 일어나나요?

**모범답안:** “인증과 사용 자격, 요청 한도를 검사한 뒤 질문과 세션 정보를 검증합니다. 저장된 전사, 요약, 최근 문답, 과거 수업과 자료 문맥 등을 독립적으로 읽을 수 있는 부분은 병렬 조회합니다. 이를 질문 맥락으로 구성해 모델 응답을 스트리밍하고 답변과 사용량 정보를 저장합니다. 검색이 실패했을 때 제공 가능한 자료와 제공하지 못한 자료를 구분하는 것도 이 흐름의 일부입니다.”

**근거:** `app/api/ask/route.ts`의 `POST`, `findLectureContext`.

### 13. RAG를 사용했나요? 직접 설명해 보세요.

**모범답안:** “필요한 자료를 찾아 모델 입력에 포함하는 RAG 요소가 있습니다. 전사와 자료를 조각으로 만들고 임베딩을 저장한 뒤 질문과 관련된 조각을 조회합니다. 다만 현재 자료 처리는 벡터 검색만으로 구성하지 않았습니다. 저장된 전체 텍스트가 문맥 예산 안에 들어오면 전체를 쓰고, 큰 자료는 키워드·의미 검색과 인접 문맥을 결합합니다. 질문 유형과 자료 크기에 따라 근거를 안정적으로 공급하는 것이 목적입니다.”

### 14. PDF를 올렸는데 AI가 못 읽는다고 했던 원인은 무엇인가요?

**모범답안:** “업로드 성공과 답변에 관련 내용이 전달되는 것은 별개였습니다. 이전 경로는 문서 첫 600자와 소수의 검색 결과에 의존했고, 최근 네 첨부만 탐색하는 제한도 있었습니다. 임베딩이나 검색 RPC가 실패하면 상세 문맥이 사라져 모델이 자료가 없다고 오해할 수 있었습니다. 지원하는 20개 첨부를 탐색하고, 저장 텍스트를 예산 내에서 포함하며, 검색 실패와 자료 부재를 구분하도록 개선했습니다.”

**꼬리질문:** 프롬프트를 고치면 끝인가요? → 프롬프트가 요구하는 근거를 실제 데이터 경로가 제공하는지 먼저 확인해야 한다.

### 15. 왜 모든 PDF 텍스트를 항상 넣지 않나요?

**모범답안:** “짧은 자료는 전체를 넣는 편이 검색 누락을 줄일 수 있지만, 길거나 많은 자료는 비용과 지연이 커지고 관련 없는 내용도 늘어납니다. 현재는 자료 전체를 공유하는 60,000자 예산을 두고, 넘으면 관련 구간을 선별합니다. 이는 문자 기준의 구현 한도이지 모든 모델의 토큰 한도나 최적값은 아닙니다. 예산을 바꾸려면 답변 품질·입력 토큰·지연을 함께 비교하겠습니다.”

### 16. 임베딩 검색이 실패하면 어떻게 되나요?

**모범답안:** “임베딩 서비스 오류가 곧 문서 내용 소실이 되지 않게 저장 텍스트와 키워드 검색 경로를 유지합니다. 질문에 맞는 구간 주변 문맥도 함께 넣고, 전체인지 일부인지 조회 실패인지 모델에 전달합니다. 모든 검색 실패에서 동일한 답변 품질을 보장하는 것은 아니지만, 확인한 근거를 유지하면서 답변 범위를 줄일 수 있습니다.”

### 17. 청크 크기는 어떻게 정했고 어떤 한계가 있나요?

**모범답안:** “전사 청킹 함수는 기본 1,800자 기준으로 구간을 묶고 시작·종료 시각을 유지합니다. 조각이 작으면 설명 관계가 끊기고, 너무 크면 검색 결과의 관련성이 떨어질 수 있습니다. 현재 값이 최적이라는 실험 결과는 제시할 수 없고, 정의·예제·비교 질문별로 필요한 근거가 포함되는지 평가해야 합니다. 구현상 하나의 입력 구간 자체가 1,800자를 넘으면 그 구간을 잘라내지는 않으므로 엄격한 최대 길이는 아닙니다.”

### 18. 키워드 검색과 벡터 검색은 무엇이 다른가요?

**모범답안:** “키워드 검색은 정확한 용어나 코드처럼 표현이 중요한 경우 유용하고, 벡터 검색은 표현이 달라도 의미가 가까운 내용을 찾는 데 도움이 됩니다. 강의 자료에는 전문 용어도 있고 ‘이거 왜 그래요?’ 같은 짧은 질문도 있어 질문과 최근 전사를 함께 활용합니다. 현재 키워드 정규화와 점수는 휴리스틱이므로 한국어 형태소 분석이나 학습된 재순위화가 구현됐다고 설명하지 않겠습니다.”

### 19. 자료의 그림과 스캔 PDF도 이해하나요?

**모범답안:** “일반 자료 문맥 경로에서 확인한 것은 PDF에서 추출해 저장한 텍스트입니다. 그래서 그 경로만으로 도표나 스캔 이미지까지 이해했다고 말할 수 없습니다. 답변 문맥에도 텍스트 근거라는 범위를 표시합니다. 그림이 핵심인 과목을 지원하려면 페이지 이미지·OCR·멀티모달 경로를 별도로 검증하고 비용과 접근 권한을 함께 설계하겠습니다.”

### 20. PDF 추출이 중간에 실패하면 어떻게 처리하나요?

**모범답안:** “일부 페이지만 읽고 전체 업로드가 성공한 것처럼 처리하면 이후 답변에서 누락을 찾기 어렵습니다. 현재는 네이티브 PDF의 모든 페이지를 읽은 후 색인을 저장하고, 중간 페이지 오류를 성공으로 처리하지 않습니다. 500페이지 제한을 넘으면 파일 분할을 안내하고, 청크별 임베딩 응답이 모두 유효한지도 저장 전에 확인합니다. 실제 12페이지 합성 PDF를 PDF.js로 읽어 각 주제가 청킹 후 남는지를 확인한 기록이 있습니다.”

### 21. 긴 강의를 매번 모델에 전부 보내나요?

**모범답안:** “요약이 있으면 완료된 구간을 요약으로 표현하고 진행 중이거나 질문이 가리키는 구간은 원문을 유지하는 경로가 있습니다. ‘방금 놓쳤어요’는 최근 90초 구간에 집중합니다. 요약이 없는 경우의 원문 경로도 남아 있습니다. 요약은 비용을 줄일 수 있지만 정보를 잃을 수 있으므로 원문을 보존하고 근거 복구가 가능한지 확인해야 합니다.”

### 22. Lecue가 온톨로지나 지식그래프를 구현한 건가요?

**모범답안:** “강의실·세션·자료 관계와 개념 카드가 있다고 산업 온톨로지나 GraphRAG를 구현했다고 보지는 않습니다. 현재는 관계형 데이터와 텍스트 검색 중심입니다. INFOCZ와 연결해서 설명할 부분은 정보의 소속과 근거를 구조화한 경험입니다. 설비 의존관계처럼 여러 관계를 따라가는 질문이 실제로 중요해진다면 개체·관계 정의와 그래프 조회를 검토하겠습니다.”

**주의:** 개발 탐색용 graphify 그래프와 Lecue 제품의 검색 아키텍처를 혼동하지 않는다.

## C. 실시간 음성·비동기·장애 대응

### 23. 음성이 텍스트가 되기까지 설명해 주세요.

**모범답안:** “브라우저에서 마이크 또는 지원되는 브라우저 탭의 오디오를 가져와 PCM으로 처리합니다. 브라우저는 서버가 발급한 짧은 수명의 일회용 티켓으로 Worker에 연결합니다. Worker는 서버의 사용 허가와 전송량 제한을 확인하며 공급자에 음성을 전달하고 전사 결과를 돌려줍니다. 임시 전사와 확정 전사, 저장 상태를 구분해야 화면 반응과 데이터 보존을 함께 다룰 수 있습니다.”

### 24. 반복 재연결 문제는 어떻게 분석했나요?

**모범답안:** “안정적인 Wi-Fi에서도 두 공급자에 걸쳐 재연결이 발생한 기록이 있어 공통 중계 경로를 확인했습니다. 공급자 연결 수립에 설정한 8초짜리 fetch 취소 신호가 WebSocket 업그레이드 이후에도 남아 정상 연결까지 끊는 것이 원인이었습니다. 연결 수립용 AbortController와 타이머를 사용하되 fetch 반환 후 타이머를 해제하도록 바꿨습니다. 실제 workerd와 로컬 WebSocket 서버에서 이전 실패를 재현하고 수정 후 시간 경계를 넘는 연결을 확인했습니다.”

**90초 확장:** 단위 테스트가 놓친 이유는 25번, 잔여 누락 경고는 26번으로 연결한다.

### 25. 테스트가 있는데 왜 이 버그를 못 잡았나요?

**모범답안:** “기존 smoke 테스트도 공급자 fetch를 직접 만든 업그레이드 응답으로 대체해 실제 네트워크 연결의 취소 동작을 재현하지 못했습니다. 테스트 수가 부족하다기보다 대체한 경계가 문제였습니다. 이후 실제 런타임과 WebSocket 네트워크를 사용해 제한 시간을 넘기는 검증을 추가했습니다. 다만 공급자는 합성이므로 실제 유료 공급자를 통한 장시간 수업 성공과는 구분합니다.”

### 26. 연결 문제를 고쳤는데도 누락 경고가 난 이유는요?

**모범답안:** “첫 연결 준비도 지연될 수 있는데, 브라우저가 먼저 캡처한 PCM을 보관하는 시간이 2초뿐이었습니다. 연결이 안정적이어도 세션 생성과 티켓 발급을 기다리며 앞부분이 버려질 수 있었습니다. 준비·복구 큐를 30초로 늘리고 실제로 버린 바이트만 누락 시간으로 환산해 안내했습니다. 경고만 없애는 것이 아니라 실제 손실과 안내가 일치하도록 바꾼 사례입니다.”

### 27. 30초 버퍼면 완전히 복구되나요?

**모범답안:** “아닙니다. 보관 한도를 넘는 중단이나 탭 종료, 공급자가 확정하기 전에 끊긴 응답까지 무손실로 복구하지는 못합니다. 전송 속도를 제한하기 때문에 보존한 음성이 쌓이면 지연이 남을 수도 있습니다. 현재 선택은 제한된 메모리로 짧은 중단의 손실을 줄이고, 실제 손실이 발생하면 숨기지 않고 알리는 것입니다.”

### 28. 밀린 음성을 한꺼번에 보내면 되지 않나요?

**모범답안:** “한꺼번에 보내면 중계의 속도 제한을 넘거나 소켓 대기량이 커질 수 있습니다. 큐는 시간에 따라 전송 허용량을 보충하고 소켓의 bufferedAmount를 보면서 보낼 양을 제한합니다. send가 실패하면 큐에 음성을 남겨 연결 전환 중에 데이터가 사라지지 않게 합니다. 빠른 복구와 서버가 허용하는 전송 속도 사이의 절충입니다.”

### 29. 녹음 종료 시 마지막 음성이 잘리는 문제는요?

**모범답안:** “사용자가 종료를 눌렀다고 이미 캡처한 음성을 즉시 폐기하면 안 됩니다. 대기 큐와 AudioWorklet의 마지막 조각을 전송한 다음 CloseStream을 보내도록 순서를 지킵니다. 전송 대기는 최대 32초로 제한하고, 전송·저장이 끝나기 전에는 저장 중 상태를 보여줍니다. 그동안 불완전한 전사로 노트를 생성하는 동작도 막습니다.”

### 30. 비동기 요청의 응답 순서가 뒤바뀌면 어떻게 하나요?

**모범답안:** “빠르게 중지하고 새 수업을 시작하면 이전 티켓 응답이나 종료 처리가 늦게 도착할 수 있습니다. 요청 시도·세션·캡처 식별자를 비교해 현재 작업에 속하는 결과만 반영해야 합니다. 자원 정리도 해당 작업이 만든 자원에만 적용합니다. 단순히 마지막에 도착한 응답을 최신 상태로 취급하면 새 녹음이 이전 작업에 의해 끊길 수 있습니다.”

### 31. STT 공급자는 왜 나눴나요? 품질은 어떻게 비교하나요?

**모범답안:** “현재 코드는 단일 언어 입력과 한국어·영어 혼용 입력의 공급자 경로를 구분합니다. 공급자 선택의 타당성은 실제 강의 조건에서 전사 오류, 전문 용어, 지연과 비용을 비교해야 합니다. CER과 용어 재현율을 계산하는 도구는 있지만, 그것만으로 특정 공급자가 모든 강의에서 더 좋다는 결과를 주장하지 않겠습니다.”

**추가:** CER 구현은 정규화 후 편집거리를 기준 문자열 길이로 나눈다. 문장부호·공백 제거 정책 때문에 표시 품질은 별도 평가해야 한다.

### 32. 온라인 강의는 화면 전체를 서버로 보내나요?

**모범답안:** “캡처 원본에는 비디오 트랙이 있을 수 있지만, STT 입력은 오디오 트랙만 가진 스트림으로 분리합니다. 탭 공유 선택, 오디오 없음, 공유 종료 같은 상태를 별도로 처리합니다. 현재 지원 판단과 실제 OS·브라우저 검증은 구분해야 하며, 설치형 회의 앱과 모든 브라우저를 지원한다고 확대해서 설명하지 않겠습니다.”

## D. 보안·과금·동시성

### 33. 왜 STT를 브라우저에서 직접 연결하지 않나요?

**모범답안:** “공급자 임시 토큰을 받는 구조만으로는 사용자가 앱의 사용량 통제를 우회하는 비용 문제를 막기 어렵습니다. 현재는 브라우저에 30초 유효 일회용 Lecue 티켓을 주고, Worker가 서버에서 받은 허가에 따라 공급자 연결과 PCM 전송을 제어합니다. 공급자 접근 권한과 실제 비용 발생 경로를 서버 측에서 관리하려는 선택입니다. 대신 중계 장애와 지연이라는 새 운영 책임이 생깁니다.”

### 34. 브라우저가 보낸 녹음 시간은 왜 믿으면 안 되나요?

**모범답안:** “클라이언트 값은 변경해서 보낼 수 있기 때문입니다. 실시간 경로는 PCM 전송량과 서버의 사용 허가를 기준으로 통제하고, 파일 업로드는 서버에서 실제 오디오를 해독해 길이를 확인한 뒤 크레딧을 예약·정산합니다. UI 타이머는 사용자 안내용이지 비용을 확정할 근거가 아닙니다.”

### 35. 인증과 권한 검사의 차이는 무엇인가요?

**모범답안:** “인증은 요청자가 누구인지 확인하는 것이고, 권한 검사는 그 사용자가 해당 세션이나 자료에 접근해도 되는지 확인하는 것입니다. 로그인한 사용자라도 다른 사용자의 sessionId를 보내면 거절해야 합니다. API 확인뿐 아니라 RLS와 소유권 제약을 함께 사용하고, 서비스 권한으로 DB에 접근하는 경로에서는 사용자 범위를 특히 명시적으로 검사해야 합니다.”

### 36. RLS가 있는데 왜 복합 외래키도 필요한가요?

**모범답안:** “자식 행의 user_id만 본인인지 확인하면, 그 행이 다른 사용자의 부모 세션을 가리키는 문제를 놓칠 수 있습니다. 복합 소유권 외래키는 자식의 사용자와 부모의 사용자가 일치한다는 관계 자체를 DB에서 강제합니다. RLS는 접근을 제한하고 FK는 관계의 무결성을 지키므로 역할이 다릅니다. 관련 수정에서는 다른 사용자의 부모를 연결하는 경계 사례를 검증했습니다.”

### 37. 파일 저장소는 어떻게 보호하나요?

**모범답안:** “브라우저가 Storage에 직접 쓰거나 지우며 서버의 검사와 예산을 우회하지 못하도록 제한했습니다. 서버에서 소유권·동의·용량을 확인해 업로드하는 경로를 사용합니다. DB 행 삭제와 실제 파일 삭제는 별도 작업이므로 실패를 재시도할 삭제 큐도 필요합니다. 다만 자동 정리 코드가 있다고 운영 예약까지 활성화됐다고 말하지는 않겠습니다.”

### 38. 결제 성공 화면으로 크레딧을 지급하면 안 되나요?

**모범답안:** “브라우저의 성공 화면이나 돌아온 URL은 신뢰할 수 있는 결제 확정 근거가 아닙니다. 서버가 Paddle 웹훅의 원문과 서명을 검증하고, 이벤트와 상품·거래 내용을 확인한 뒤 DB 함수로 반영합니다. 화면 복귀는 상태를 다시 조회하는 계기이고, 크레딧 지급의 권한은 검증된 서버 경로에 둡니다.”

### 39. 웹훅이 두 번 오거나 두 요청이 동시에 오면요?

**모범답안:** “같은 이벤트를 여러 번 전달받는 상황을 정상적으로 예상해야 합니다. 이벤트 ID를 기록하고 크레딧 반영을 같은 원자적 처리 안에서 수행해 중복 지급을 막습니다. 단순히 처리 여부를 읽은 뒤 별도로 지급하면 동시 요청이 모두 미처리 상태를 볼 수 있습니다. 요청이 한 번만 온다고 가정하기보다 중복되어도 결과가 같게 만드는 것이 멱등성입니다.”

### 40. 세션 시작 요청이 타임아웃되면 재시도해도 되나요?

**모범답안:** “타임아웃이 곧 서버에서 생성되지 않았다는 뜻은 아닙니다. 같은 시작 작업에 같은 request ID를 재사용하고, DB에서 사용자와 request ID의 유일성을 보장합니다. 중복 삽입 충돌이 나면 먼저 만들어진 세션을 다시 조회해 반환합니다. 새 ID로 무조건 재시도하면 수업이 중복 생성될 수 있습니다.”

### 41. 노트 생성 버튼을 여러 탭에서 누르면요?

**모범답안:** “프로세스 메모리의 플래그는 다른 서버나 탭의 요청까지 막지 못하므로 DB에서 생성 임대를 원자적으로 확보합니다. 권한을 얻지 못한 요청은 모델을 호출하지 않습니다. 완료 시에는 요청별 토큰이 일치할 때만 해제해 오래된 요청이 새 작업의 임대를 지우지 못하게 합니다. 중단된 작업의 임대는 만료 후 다시 확보할 수 있습니다.”

**꼬리질문:** 정확히 한 번 생성되나요? → 임대 만료나 외부 호출 후 강제 종료까지 포함한 정확히 한 번 실행을 보장한다고 말하지 않는다.

### 42. 요약 생성이 중간에 실패하면 비용을 또 쓰나요?

**모범답안:** “구간별로 완료한 요약을 저장해 다음 요청에서 재사용하도록 했습니다. 덕분에 뒤쪽 구간이 실패해도 처음부터 모두 다시 생성할 필요는 없습니다. 다만 공급자가 처리한 뒤 저장 전에 프로세스가 죽으면 호출 비용과 저장 결과가 어긋날 수 있습니다. 외부 모델 호출과 DB 저장을 하나의 트랜잭션처럼 취급할 수 없다는 한계가 있습니다.”

### 43. 비용을 어떻게 줄였고 얼마나 줄었나요?

**모범답안:** “품질을 낮추는 모델 교체보다 중복 생성 차단, 완료 요약 재사용, 필요한 문맥 구성 같은 낭비 감소를 먼저 적용한 기록이 있습니다. 중복 요청이 실제로 있을 때 절감되므로 사용량 분포 없이 전체 비용이 몇 퍼센트 줄었다고 말할 수는 없습니다. 전사 시간, 모델 입출력 토큰, 검색 호출, 저장·전송량을 분리해 사용자당 변동비와 매출을 비교하겠습니다.”

### 44. 분당 과금인데 질문을 무제한 보내면 손해 아닌가요?

**모범답안:** “녹음 시간의 크레딧만으로 모델 호출량을 충분히 제한할 수는 없습니다. 현재 ask 경로에는 사용자별 분당 20회 제한과 기본 플랫폼 키 기준 일일 300회 제한이 있고, 사용 자격도 검사합니다. 개인 키 경로와 플랫폼 비용 경로를 구분하지만 모든 요청에 자원 비용이 없는 것은 아닙니다. 제한값이 적절한지는 실제 사용 분포와 상위 사용자의 비용을 보고 조정해야 합니다.”

### 45. 프롬프트 인젝션과 생성 결과 보안은요?

**모범답안:** “자료에 쓰인 지시를 시스템 권한으로 받아들이면 안 됩니다. 프롬프트의 구분만으로 완전 방어를 주장하지 않고, 조회 권한과 사용할 수 있는 도구 범위를 서버에서 제한해야 합니다. 생성 결과도 신뢰하지 않아야 하므로 Mermaid에는 허용 문법 검사와 외부 요청 문법 차단을 적용한 기록이 있습니다. 자료 속 공격 지시와 외부 링크·렌더링 우회는 별도 공격 사례로 검증하겠습니다.”

### 46. 백업과 삭제는 운영 준비가 끝났나요?

**모범답안:** “암호화 DB 백업과 합성 데이터 복구 검증 기록은 있습니다. 그러나 DB 백업에 PDF·오디오 원본과 일부 인증 정보까지 모두 들어 있는 것은 아닙니다. 최근 배포 기록상 지속적 백업과 정기 파일 삭제 예약은 비활성 상태가 남아 있습니다. 구현, 일회성 검증, 정기 운영을 각각 구분하고, 복구 목표와 원본 복구 범위를 추가로 정해야 합니다.”

## E. 검증·성과·운영 판단

### 47. 환각을 어떻게 줄였나요?

**모범답안:** “확인한 전사와 자료를 제공하고, 자료가 전체인지 일부인지 조회에 실패했는지 함께 전달합니다. 특히 이전 AI가 ‘자료를 볼 수 없다’고 한 답보다 현재 확보한 자료 근거가 우선하도록 했습니다. 그렇더라도 근거가 있다고 답이 항상 맞는 것은 아니므로 답변의 주장과 근거가 실제로 연결되는지 평가해야 합니다. 환각을 없앴다고 표현하지 않겠습니다.”

### 48. 답변 품질을 어떻게 검증했나요?

**모범답안:** “문맥 구성 회귀 테스트와 실제 모델 답변 평가를 구분합니다. 9월 7일 기록에는 합성 질문 네 건을 실제 API로 실행해 형식과 핵심 내용을 확인한 결과가 있습니다. 그러나 네 건은 표본이 작고 인증·자료 업로드·저장까지 포함한 전체 앱 시험도 아닙니다. 다음에는 자료 근거 질문, 근거 없는 질문, 모호한 지시어, 전문 용어, 한영 혼용 등을 포함한 고정 평가 세트를 만들겠습니다.”

### 49. 지연 시간 수치는 있나요?

**모범답안:** “그 네 건의 합성 평가에서는 실제 첫 텍스트까지 평균 2.332초, 완료까지 평균 3.362초였다는 기록이 있습니다. 응답 헤더가 아니라 텍스트 delta를 측정했지만 운영 전체 지연이나 p95는 아닙니다. 실서비스에서는 인증, 검색, 모델 첫 토큰, 완료와 저장을 구분해 측정하고 질문 유형별 분포를 보겠습니다.”

**주의:** 평가 이후 프롬프트 문구 추가가 있었고 그 최종 문구의 재평가는 하지 않았다는 기록도 있다.

### 50. 테스트 483개면 충분한가요?

**모범답안:** “숫자 자체로 충분함을 판단하지 않습니다. 최신 PCM 큐 수정 기록에서는 전체 앱 테스트 483개와 타입 검사가 통과했지만, 실제 공급자 장시간 강의나 실제 결제까지 검증한 뜻은 아닙니다. 금전·권한은 DB 경합 검증, PDF는 실제 파서, 연결은 실제 런타임처럼 실패가 생길 경계를 검증해야 합니다. 이번 문서 작성에서는 테스트를 다시 실행하지 않았습니다.”

### 51. 실제 서비스 운영을 했다고 말할 수 있나요?

**모범답안:** “현재 무료 이용자가 약 20~30명 있고 유료 결제도 1건 발생했습니다. 따라서 배포만 한 프로젝트를 넘어 실제 사용 단계에 들어간 제품이라고 설명할 수 있습니다. 지금은 무료 기간 종료 후 전환을 높이기 위해 계속 유지보수하고 있습니다. 다만 표본이 작고 체험이 끝나지 않은 이용자도 있으므로 제품 시장 적합성이나 안정적인 매출이 검증됐다고 보지는 않습니다.”

### 52. 장애가 생기면 무엇을 먼저 보나요?

**모범답안:** “먼저 영향 범위를 사용자·세션·입력 방식·발생 시점으로 좁히고, 데이터 손실이나 과금 이상이 있는지 확인하겠습니다. 그다음 캡처, 중계, 공급자, 저장, 검색, 생성 중 마지막으로 성공한 단계를 찾습니다. 원본 강의 내용 없이 연결 시간과 종료 코드 같은 메타데이터로 확인할 수 있는 것부터 보겠습니다. 대응 후에는 같은 장애를 재현하는 테스트와 남은 확인 범위를 기록하겠습니다.”

### 53. 지금 가장 큰 약점은 무엇인가요?

**모범답안:** “무료 이용자 20~30명과 결제 1건은 초기 신호지만, 반복 사용과 체험 종료 후 전환을 설명하기에는 아직 데이터가 적습니다. 그래서 지금은 기능 수를 늘리기보다 자료 기반 답변과 음성 안정성처럼 계속 사용할 이유에 직접 영향을 주는 문제를 개선하고 있습니다. 앞으로 체험이 끝난 이용자 집단의 재사용·결제 여부와 중단 이유를 함께 확인하겠습니다. 유지보수를 했다는 사실과 전환율이 실제로 올랐다는 결과는 구분하겠습니다.”

### 54. 동시 사용자가 1,000명이 되면 어떻게 하나요?

**모범답안:** “가입자 1,000명인지 동시 음성 연결 1,000개인지 먼저 구분하겠습니다. 동시 연결이라면 32,000바이트/초 PCM 기준 음성 입력만 약 32MB/초이고, 중계에서 공급자로 나가는 구간과 프로토콜 오버헤드는 별도입니다. 공급자 동시성, 중계 연결·허가 갱신량, DB 부하, AI 요청량을 나눠 합성 부하로 측정하겠습니다. 아직 1,000명 처리 성능을 검증했다고 말할 수는 없습니다.”

### 55. 다시 만든다면 무엇을 바꾸겠나요?

**모범답안:** “초기에 평가 자료와 단계별 관측 지표를 먼저 두겠습니다. PDF 사건은 업로드 상태와 실제 문맥 공급 상태가 다르다는 것을, 재연결 사건은 모킹으로 가린 실행 환경이 있다는 것을 보여줍니다. 모든 구조를 재작성하기보다 이 경계를 더 잘 보이게 만들고 실제 사용자에게 중요한 흐름부터 검증하겠습니다.”

## F. FDE 케이스·압박 질문·협업

### 56. 고객이 ‘AI가 자꾸 틀린다’고 하면 어떻게 하겠나요?

**모범답안:** “먼저 틀린 답 세 건과 고객이 기대한 답·근거를 요청하겠습니다. 사실 오류, 자료 누락, 다른 문서 참조, 답변 형식 불만을 구분하고 같은 입력으로 재현하겠습니다. 필요한 근거가 저장돼 있는지, 검색됐는지, 모델 입력에 들어갔는지 순서대로 확인하겠습니다. Lecue의 PDF 문제처럼 검색 실패를 모델 성능 문제로 오해할 수 있으므로 단계별 증거를 보고 수정하겠습니다.”

### 57. 고객의 데이터가 문서마다 다르게 적혀 있다면요?

**모범답안:** “같은 대상을 무엇으로 식별하는지와 충돌 시 어떤 원본이 우선인지부터 확인하겠습니다. 예를 들어 설비명이 같아도 공장·라인·유효 시점이 다르면 다른 대상일 수 있습니다. 원본 식별자와 정규화한 식별자를 함께 보존하고, 확실하지 않은 병합은 검토 대상으로 남기겠습니다. 그다음 고객이 실제로 답해야 하는 질문을 소수 선정해 데이터 모델이 충분한지 확인하겠습니다.”

### 58. 고객은 빨리 배포하라는데 품질이 부족하면요?

**모범답안:** “배포 범위와 실패 영향을 먼저 나누겠습니다. 권한 누출이나 잘못된 과금처럼 피해가 큰 문제는 막고, 답변 표현 개선처럼 복구 가능한 문제는 제한된 사용자에게 단계적으로 검증할 수 있습니다. 고객과 성공 기준·중단 기준·담당자를 정하고 가능한 범위를 설명하겠습니다. 일정이나 정확도를 근거 없이 약속하기보다 확인 가능한 작은 결과를 먼저 만들겠습니다.”

### 59. 고객별 요구를 다 넣으면 제품이 복잡해지지 않나요?

**모범답안:** “요청한 화면이나 기능 뒤에서 실제 업무 목적을 먼저 확인하겠습니다. 여러 고객에게 반복되는 문제는 공통 기능으로, 한 고객의 데이터 차이는 변환 규칙이나 설정으로 해결할 수 있는지 보겠습니다. 다만 아직 고객이 하나인데 범용 플랫폼부터 만드는 것도 비용입니다. 실제 반복이 확인되는 범위에서 공통화하겠습니다.”

### 60. AI 도구가 거의 다 만든 것 아닌가요?

**모범답안:** “AI와 함께 개발했고, 약 5일 만에 제품을 빌드하는 데 그 도움을 받았습니다. 그래서 모든 코드를 혼자 타이핑했다는 식으로 설명하지 않겠습니다. 중요한 것은 실제 이용자가 쓰는 과정에서 무엇이 문제인지 판단하고, 수정된 동작과 남은 한계를 이해하는 것이라고 생각합니다. 예를 들어 검색 실패와 자료 부재의 차이, 연결 수립 타이머가 이미 연결된 소켓을 끊는 문제를 코드와 연결해 설명하겠습니다. AI가 만든 코드라도 제가 충분히 이해하지 못한 부분은 추가로 검증해야 하는 제 책임이라고 생각합니다.”

**연습:** PDF 실패 경로, PCM 큐, 중복 웹훅 중 하나를 골라 AI 없이 핵심 의사코드를 설명한다.

### 61. 코딩테스트 경험이 없는데 실무 구현은 가능한가요?

**모범답안:** “코딩테스트 경험이 없는 것은 맞습니다. 다만 Lecue를 빌드하고 실제 이용자가 있는 상태에서 유지보수하는 경험을 쌓고 있습니다. 제품 개발 경험과 제한 시간 안에 혼자 코드를 작성하는 역량이 동일하다고 생각하지는 않습니다. 코딩 문제에서는 먼저 입력·출력과 예외를 확인하고 단순한 동작부터 구현한 뒤 검증하겠습니다. 막히는 부분도 현재 가설과 필요한 정보를 말로 설명하겠습니다.”

### 62. 모르는 기술을 쓰라는 요청이 오면요?

**모범답안:** “목표 동작과 필수 제약을 먼저 정한 다음 공식 문서와 작은 실행 예제로 확인하겠습니다. Lecue의 연결 문제처럼 라이브러리 이름이 같아도 런타임 동작이 다를 수 있으므로 실제 배포 환경의 경계를 확인하는 것이 중요합니다. 막힌 부분은 재현 코드, 현재 가설과 확인 결과를 정리해 동료에게 질문하겠습니다.”

### 63. 동료와 기술 선택에 의견이 다르면요?

**모범답안:** “먼저 서로 중요하게 보는 기준이 품질, 일정, 비용, 유지보수 중 무엇인지 맞추겠습니다. 예를 들어 검색만 쓸지 전체 텍스트도 넣을지 의견이 다르면, 같은 질문 세트에 대한 근거 누락과 지연·토큰 비용을 비교할 수 있습니다. 측정 결과와 되돌리기 쉬운 범위를 기준으로 결정하겠습니다. 이는 제가 적용할 의사결정 방식이며, 실제로 있었던 팀 내 갈등 사례라고 포장하지 않겠습니다.”

### 64. 왜 당신을 FDE로 뽑아야 하나요?

**모범답안:** “제가 보여드릴 수 있는 강점은 사용자에게 보이는 문제를 데이터와 실행 흐름으로 나누어 설명하고, 수정 결과를 검증 범위와 함께 말하는 태도입니다. Lecue에서 자료를 올렸는데 답이 안 되는 상황, 실시간 연결, 권한과 비용 같은 제품 문제를 다뤘습니다. 산업 현장 경험과 코딩 속도는 더 쌓아야 하지만, 모르는 것을 분명히 하고 작은 재현과 검증으로 문제를 좁히는 방식으로 기여하고 싶습니다.”

**설명 포인트:** 약 5일간의 빌드 → 실제 무료 이용자 20~30명 → 결제 1건 → 전환을 위한 유지보수라는 흐름을 함께 제시한다. 회사의 산업 문제를 이미 해결해 봤다는 뜻으로 말하지 않는다.

## F-2. 5일 개발·실사용·유료 전환 꼬리질문

### 65. 5일 만에 이 정도를 만들었다면 완성도가 낮지 않나요?

**모범답안:** “약 5일은 빌드 기간이고, 이후에도 계속 유지보수하고 있습니다. 짧은 개발 기간 자체를 품질의 근거로 내세우지는 않겠습니다. 실제 이용자가 생긴 뒤 자료 검색이나 음성 연결에서 개선할 부분이 드러났고, 이를 다루는 과정까지 제 경험입니다. 빠른 구현의 장점은 실제 사용을 일찍 확인한 것이고, 그만큼 검증과 안정화 책임이 뒤따른다고 생각합니다.”

### 66. 무료 이용자는 20~30명인데 결제가 1건뿐이면 실패 아닌가요?

**모범답안:** “현재 숫자만으로 성공이라고 주장하지도, 실패라고 확정하지도 않겠습니다. 아직 무료 기간이 끝나지 않은 이용자가 있어 최종 전환을 판단하기 이릅니다. 다만 무료 사용과 지불 의사는 다르므로 1건의 결제에 만족해서는 안 됩니다. 체험이 끝난 이용자 중 누가 반복 사용했고 왜 결제하거나 중단했는지 확인해 가치 부족, 사용 장애, 가격 문제를 구분하겠습니다.”

### 67. 현재 전환율은 몇 퍼센트인가요?

**모범답안:** “현재 확실히 말씀드릴 수 있는 수치는 무료 이용자 약 20~30명과 유료 결제 1건입니다. 결제 건수와 결제한 고유 사용자 수가 같은지도 확인해야 하고, 체험 종료 시점도 다르므로 단순히 나눠 확정 전환율이라고 부르기는 어렵습니다. 같은 시기에 체험을 시작해 관찰 기간이 끝난 이용자 중 일정 기간 안에 처음 결제한 고유 사용자 비율로 정의해 보겠습니다.”

**꼬리질문:** 분모를 유리하게 고르는 것 아닌가요? → 체험 시작자 전체와 체험 종료 집단을 함께 보고, 집계 기간·제외 기준을 고정한다고 답한다.

### 68. 전환율을 높이기 위해 구체적으로 무엇을 하고 있나요?

**모범답안:** “현재는 지속적인 유지보수로 핵심 경험을 개선하고 있습니다. 자료를 업로드해도 답변이 근거를 못 찾거나 강의 음성이 빠지면 결제할 이유가 약해지기 때문입니다. 그래서 자료 문맥 전달과 음성 연결·대기 큐 같은 신뢰성 개선을 전환의 선행 조건으로 보고 있습니다. 다만 이 수정으로 전환율이 올랐다는 측정 결과는 아직 없으며, 체험 종료 후 반복 사용과 결제를 확인해야 합니다.”

### 69. 유지보수와 전환율이 관련 있다는 가설은 어떻게 검증하나요?

**모범답안:** “문제가 발생한 이용자와 발생하지 않은 이용자의 재사용·중단 경향을 먼저 확인하겠습니다. 수정 전후로는 자료 질문의 실패율이나 음성 누락 같은 직접 지표를 보고, 이후 재사용과 결제까지 연결해서 보겠습니다. 20~30명에서는 통계적으로 강한 A/B 실험 결론을 내기 어려우므로 개별 사용 흐름과 짧은 인터뷰를 함께 보겠습니다. 전후 변화만으로 유지보수가 원인이라고 단정하지 않겠습니다.”

### 70. 다음 한 주 동안 무엇을 가장 먼저 하겠나요?

**모범답안:** “실제 이용을 막는 장애를 우선 확인하고, 현재 체험 이용자가 수업을 끝까지 진행하며 질문에 도움을 받는지 보겠습니다. 그다음 반복 사용 여부와 체험 종료일·첫 결제를 같은 기준으로 확인할 수 있게 정리하겠습니다. 결제하지 않은 이유가 신뢰성인지 가치 전달인지 가격인지 알아야 다음 작업을 정할 수 있습니다. 큰 신규 기능보다 실제 중단 이유 하나를 해결하는 것을 우선하겠습니다.”

### 71. 유료 결제 1건의 의미는 무엇인가요?

**모범답안:** “누군가가 실제로 돈을 지불했다는 점에서 무료 사용보다 강한 초기 신호입니다. 하지만 1건으로 반복 매출, 고객 유지, 수익성이 입증되지는 않습니다. 결제한 사용자가 어떤 가치를 얻었고 이후에도 사용하는지 확인하면 제품 방향을 정하는 데 도움이 될 것입니다. 현재 단계에서는 첫 지불 경험이 발생했고 이를 반복 가능한 사용 가치로 이어가려는 중이라고 설명하겠습니다.”

### 72. 사용자 피드백이 들어오면 무엇부터 고치나요?

**모범답안:** “먼저 수업을 진행할 수 없는 장애와 권한·과금 문제를 가장 높은 우선순위로 두겠습니다. 그다음 답변 근거 누락처럼 핵심 가치에 영향을 주는 문제, 마지막으로 편의 기능을 보겠습니다. 이용자 수만으로 판단하지 않고 한 번 발생해도 데이터 손실이나 잘못된 결제처럼 영향이 큰 문제는 먼저 다룹니다. 현재 유지보수도 무료 이용자가 계속 사용할 수 있는 신뢰성을 확보하는 관점으로 설명할 수 있습니다.”

## G. Lecue 기반 코딩·디버깅 실습 8개

실제 INFOCZ 출제 유형이나 기출이 아니다. 이메일에 명시된 기본 기술 역량과 사고 과정 설명을 함께 연습하기 위한 문제다. 아래 답은 구현 전 말로 설명할 모범 접근이다. AI 없이 익숙한 언어로 직접 작성하고 입력 예시를 실행한다.

### 실습 1. 전사 구간 중복 제거

**문제:** `{sessionId, segmentId, text}` 배열에서 같은 세션·구간의 중복을 제거하라.

**먼저 질문:** 중복된 내용이 다르면 첫 값과 마지막 값 중 무엇을 보존하나요? 출력 순서는 무엇인가요?

**모범 접근:** “마지막 값을 보존한다고 합의하면 `(sessionId, segmentId)` 복합 키의 Map에 갱신하겠습니다. 순서가 시간순이어야 한다면 시각 필드를 추가로 받아 정렬합니다. 단순 중복 제거는 평균 O(n), 정렬까지 하면 O(n log n), 저장 공간은 O(n)입니다.”

**검증:** 빈 배열, 같은 ID가 다른 세션에 존재, 내용이 다른 중복. 구분자 충돌이 없는 복합 키 표현을 사용한다.

### 실습 2. 전사 구간을 글자 수에 맞춰 청킹

**문제:** 시각과 텍스트가 있는 구간을 지정한 글자 수 기준으로 묶어라.

**먼저 질문:** 한 구간 자체가 한도를 넘으면 잘라도 되나요? 입력은 시간순인가요? 한글·이모지 길이의 기준은 무엇인가요?

**모범 접근:** “시간순 입력에서 빈 텍스트를 건너뛰고, 구분자를 포함한 누적 길이가 한도를 넘으면 현재 청크를 확정하겠습니다. 시작 시각은 첫 구간, 종료 시각은 마지막 구간을 유지합니다. 엄격한 최대 길이라면 긴 단일 구간을 나누는 규칙이 추가로 필요합니다.”

**검증:** 정확히 한도, 한도+1, 빈 텍스트, 한도보다 긴 단일 구간. 누적 문자열 복사의 비용을 무시하고 무조건 O(n)이라고 말하지 않는다.

### 실습 3. 누락된 오디오 시간 계산

**문제:** 16kHz, mono, 16-bit PCM에서 320,000바이트가 버려졌다면 몇 초인가?

**모범답안:** “초당 16,000샘플 × 1채널 × 2바이트 = 32,000바이트이므로 10초입니다. 30초 큐는 960,000바이트이고, 초기 큐가 비어 있고 전송이 전혀 없는 40초 캡처라면 10초분을 버리게 됩니다.”

**검증:** 음수·비정상 값 거절, 샘플 경계, 코덱이 바뀌면 이 식을 그대로 쓰지 않는 이유 설명.

### 실습 4. 중복 결제 이벤트 처리

**문제:** 같은 이벤트가 두 서버에 동시에 도착해도 크레딧을 한 번만 지급하라.

**모범 접근:** “DB 트랜잭션 안에서 이벤트 ID를 유일 키로 기록하고, 새로 기록된 경우에만 크레딧을 지급하겠습니다. 처리 완료와 지급 기록은 함께 커밋되어야 합니다. 메모리 Set이나 먼저 SELECT하는 것만으로는 서버 간 경합을 해결하지 못합니다.”

**검증:** 순차 중복, 동시 중복, 지급 중 예외 시 롤백. 실제 결제에서는 이 처리 이전에 서명과 거래 내용도 검증한다.

### 실습 5. 사용 시간 집계

**문제:** 사용자별 세션 시작·종료 로그에서 일일 사용 시간을 계산하라.

**먼저 질문:** 겹치는 세션은 합산하나요? 자정을 넘는 구간은 어느 날에 속하나요? 종료 누락·시간대·중복 로그는 어떻게 처리하나요?

**모범 접근:** “정책을 정한 뒤 유효한 구간을 날짜 경계로 나눠 집계하겠습니다. 겹치는 시간을 한 번만 세면 사용자별 구간을 정렬한 뒤 병합합니다. 구간 수 n에 대해 정렬이 O(n log n), 병합이 O(n)입니다. 종료 누락을 임의로 현재 시각으로 채우면 과금이 달라지므로 명시적 규칙이 필요합니다.”

### 실습 6. 문서 검색 결과 병합

**문제:** 키워드 검색과 벡터 검색 결과를 중복 없이 합쳐 상위 k개를 반환하라.

**먼저 질문:** 같은 청크 판정은 무엇인가요? 두 점수의 범위가 같나요? 동점 순서는요?

**모범 접근:** “문서 ID와 청크 ID로 병합하고 두 검색 점수를 별도로 보존하겠습니다. 임의로 원점수를 더하기 전에 정규화나 순위 결합 정책을 정합니다. 단순 구현은 병합 후 정렬해 O(n log n)이며, n이 크고 k가 작을 때만 힙을 고려하겠습니다.”

**검증:** 중복, NaN, 빈 결과, 다른 사용자의 결과가 섞이지 않도록 조회 단계의 권한 경계 확인.

### 실습 7. 오래된 응답이 새 상태를 덮어쓰는 버그

**문제:** A 수업 연결을 시작했다 취소하고 B를 시작했는데 A의 응답이 늦게 왔다.

**모범 접근:** “시작마다 operation ID를 만들고 await 이후 현재 ID와 비교하겠습니다. 일치하지 않으면 결과를 적용하지 않고 A가 만든 자원만 정리합니다. A의 finally에서 전역 소켓을 무조건 닫으면 B까지 닫히므로 정리할 자원의 소유 작업도 확인해야 합니다.”

**검증:** A 성공이 B 뒤에 도착, A 실패가 B 뒤에 도착, 두 번 취소, 컴포넌트 종료.

### 실습 8. 8초 후 연결이 끊기는 코드 디버깅

**문제:** WebSocket 연결에 사용한 fetch에 `AbortSignal.timeout(8000)`이 붙어 있다. 연결 후에도 약 8초에 끊긴다.

**모범 접근:** “연결 수립 제한인지 전체 연결 수명 제한인지 의도부터 확인하겠습니다. 런타임이 업그레이드 후에도 취소 신호를 유지하는지 실제 네트워크로 재현하고, 수립 완료 시 타이머를 해제하는 방식으로 바꾸겠습니다. 정상 연결 유지뿐 아니라 연결 수립 실패 시 제한 시간도 여전히 동작하는지 확인하겠습니다.”
